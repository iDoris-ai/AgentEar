# 计划：菜单国际化 + 泰语支持

状态：**v2，已过一轮 codex 评审并按意见重写**（2026-08-22）
前置：v0.2.3 修掉「非中文转写被当日志丢弃」，`f345524` 按评审意见收紧了解析。

> **v1 被判「需要重大修改」的两条阻断问题**（已在本版修正，记下来免得回退）：
> 1. 计划把模型下载到 `vendor/models/`，而它在打包后解析到
>    `AgentEar.app/Contents/Resources/vendor` —— **写签名 bundle 内部**，
>    会破坏签名封印、`/Applications` 下可能不可写、且每次重新打包或升级
>    都被整个替换掉，下载的模型直接消失。见 §4。
> 2. 执行顺序自相矛盾：一边说「拿到真实语料前不能定档位」，一边让下载器
>    （要固化 URL、SHA-256、体积）排在真实语料测试之前。见 §5。

本文覆盖两件独立的事，容易被混为一谈，先划清：

| | 说的是什么 | 由谁决定 |
|---|---|---|
| **界面语言** | 菜单栏那些字显示成中文还是英文还是泰文 | 用户在菜单里选，默认 **English** |
| **识别语言** | 用哪个 ASR 引擎、按什么语言解码音频 | 中/英/日/韩自动检测；**泰语必须显式选** |

两者互不影响：界面切成泰文不改变识别行为，识别切成泰语也不改变菜单文字。

## 0. 已实测确认的事实（计划的依据）

1. **SenseVoice 覆盖中、英、粤、日、韩**，中英混合的中文部分没问题。
   英文实测完全正确（v0.2.3 修复后）。
2. **中英混合里的英文技术术语必错**。Docker → `doocca`、Kubernetes →
   `cuubber needs`、raw → row/road/ro/roll。这是 M2 术语纠错的职责，
   换 ASR 模型解决不了，本计划不碰。
3. **泰语不可用，且语种标记不可信**。两次实测：

   | 样本 | SenseVoice 输出的标记 | 正文 |
   |---|---|---|
   | jason 录的泰语 | `<\|en\|>` | `Satly cr 봄金冷兔 or passa tie` |
   | `say -v Kanya` 合成 | `<\|yue\|>` | `s what Lee cr 봄 gar榔토up赣lu 점심 pass sat tie。` |

   同一语言两次给出两个不同的错误标记。**结论：不能按语种标记自动路由到
   泰语引擎。** 这是本计划最重要的一条约束——它排除了「全自动、零设置」
   的方案。
4. **whisper.cpp 在工作区里但没构建过**：`/Users/jason/Dev/tools/whisper.cpp`，
   HEAD `7de8dd78`，无 `build/bin`，`models/` 下只有 `for-tests-*` 的
   几百 KB 桩文件，**没有任何可用的真实模型**。
5. **macOS 自带泰语 TTS 嗓音 `Kanya`**，可用于冒烟测试。
   **但它不能用来算 CER**（见 §3 的风险）。

## 1. 阶段 A：菜单国际化（界面语言）

### 现状

`src/tray.rs` 里所有菜单文案都是硬编码中文字面量，约 20 处。

### 要做的

1. 抽一个 `src/i18n.rs`：

   ```rust
   pub enum Lang { En, Zh, Th }   // 默认 En

   /// 语言**显式传入**，不做全局单例。
   pub fn t(lang: Lang, key: Key) -> &'static str;
   ```

   **签名里必须带 `lang`**，不能是 `t(key)` 配一个全局「当前语言」。
   v1 写的是后者，但没说这个全局状态存在哪——而 `static mut` / `Cell` /
   `RefCell` 全局在这里都不能用（工作线程和主线程都会读）。显式传参
   最干净，零隐式状态，也顺便让「谁需要翻译」在类型上看得见。

   实际上**只有主线程需要翻译**：菜单在 `menuNeedsUpdate:` 里建，
   标题在主线程 timer 里刷。工作线程只更新原子状态位，不碰文案。
   所以根本不需要跨线程的 i18n 单例。`title()` 也改成 `title(lang)`。

   用 `enum Key` 而不是字符串 key，但**要说清它保证什么**：只有写成对
   `(Lang, Key)` 的穷尽匹配、**不出现 `_` 通配分支**，漏翻才是编译错误。
   写成 `Lang::Th => match key { Key::Quit => "ออก", _ => english(key) }`
   就退化成静默漏翻了。编译器也管不了「泰文栏里误粘了英文」「占位符
   对不上」「菜单太宽」——这些要靠快照测试 + 人工过一遍。

2. `Config` 加 `ui_lang: Lang`，**默认 `Lang::En`**，
   `#[serde(rename_all = "snake_case")]`。

   ⚠️ **`#[serde(default)]` 只挡字段缺失，挡不住未知取值。**
   配置里出现 `"ui_lang": "fr"` 会让**整个 `Config` 反序列化失败**，
   而 `config.rs` 的失败处理是「退回默认值」——结果是输入设备、触发键、
   保留期**全部被重置**，不只是语言。这个坑现在就存在，加枚举会放大它。
   要么给未知值单独兜底（自定义 `Deserialize`，未知 → 默认且保留其他字段），
   要么把每个字段做成独立容错。测试要覆盖：缺字段、三个合法值、未知值、
   类型错误。

3. 菜单加「Language」子菜单：`English` / `中文` / `ไทย`，带勾选态。

4. 切换**不需要重启**，但措辞要准确：不是「当前打开的菜单原地重绘」。
   实际是——点击 → 菜单关闭 → 状态栏标题在 ≤0.5s 内变 → **下次展开菜单
   才是新语言**。这个体验可以接受，不值得为「原地重绘」额外做事。

### 需要注意的

- **要翻译的范围比「tray.rs 那 20 个字符串」大**：
  `config.rs::Trigger::label()` 返回中文；`Info.plist` 的
  `NSMicrophoneUsageDescription` 只有中文；权限缺失提示、「需重启生效」、
  以及后面下载功能的全部状态文案（进行中/失败/校验失败/磁盘不足）。
- **状态标题里的「转写中」也要翻译**（`tray.rs::title()`）。
- **动态拼接的文案**（`■ 停止录音（已录 12s）`、`系统默认（设备名）`）
  要走带类型的 formatter，不能随手 `format!`，否则占位符对不上编译器不管。
- 日志文案**不翻译**，保持中文。但要先分清**哪些错误只写日志、哪些必须
  呈现给用户**——菜单栏应用没有终端窗口，只写日志等于用户看不见。
- **泰文 UI 需要母语者过一遍**，机器翻译不能直接当验收通过。

### 验收

- 默认全新配置启动 → 菜单是英文
- 切中文 → 下次展开是中文；重启后仍是中文
- 切泰文 → 菜单是泰文，**且不影响识别行为**
- 老的 `config.json`（没有 `ui_lang` 字段）能正常加载，语言取默认 En
- **`ui_lang` 是未知值时，只有语言退回默认，其他设置不受影响**
- 三种语言 × 全部 `Key` 的快照测试

## 2. 阶段 B：识别语言的选择方式

### 为什么 v1 用显式选择（v2 收窄了这个结论的措辞）

§0.3 已实测：泰语的语种标记在 `en` 和 `yue` 之间乱跳。这**足以否定
「用 SenseVoice 的语种标记决定要不要切 whisper」这条具体路线**——
SenseVoice 从不认为那是泰语。

但 v1 把它写成了「泰语不能自动路由，全自动方案已排除」，**这是过头了**。
两个样本只能否定这一个探针，证明不了不存在别的判别器。理论上还有：
独立的轻量语种识别模型、whisper 自己的 language detection、对输出做
乱码/脚本异常检测、双引擎跑完比分数。

这些也没那么轻松：whisper 一旦加载到能可靠判语种，多半直接拿它转写就行了，
自动路由省不下什么；两个引擎的置信度不可直接横比；SenseVoice 现有接口
看不到稳定的 confidence；乱码检测会误伤中英技术术语和短句；双引擎会同时
推高延迟、峰值 RSS 和功耗。

**所以准确的表述是**：目前没有一个经真实数据验证、且符合延迟与内存预算的
泰语自动路由器；SenseVoice 的语种标记已被证明不能充当这个角色。
**v1 用显式选择，自动路由列为后续实验项**，不是「已排除」。

### 方案

菜单加「Recognition / 识别语言」子菜单，两项：

```
Recognition ▸
  ✓ Auto (Chinese / English / Japanese / Korean)   ← 默认，走 SenseVoice
    ไทย Thai                                        ← 走 whisper，需先下载模型
```

只有两项，因为**真实的分叉只有一个**：用 SenseVoice 还是用 whisper。
中英日韩在 SenseVoice 里是同一份权重、同一次推理，再列出来只是假选项。

`Config` 加 `asr_lang: AsrLang { Auto, Thai }`，默认 `Auto`。

### 快捷键要不要

**先不加。** 理由：jason 本人日常不说泰语，切换是低频操作（给泰国同学演示
时才用），菜单够了。真出现「一场对话里中泰来回切」的需求再加，那时才知道
该绑什么键。现在加等于凭空猜一个绑定。

## 3. 阶段 C：泰语引擎选型（ADR-0004）

### 候选（v2 重排：泰语专用微调模型优先，不是通用 whisper）

jason 提的方向对：**泰语专用模型比通用 whisper 更小更准**。查过 HF 之后，
候选集变了——关键在于**这些泰语模型多数就是 Whisper 架构的微调版，
可以转成 GGML 用同一个 whisper.cpp 二进制跑，不引入任何新运行时**。

#### 判据一：decoder 层数预测「还认不认得英语」

这是选型的核心，先说清楚，否则会照着体积表选错。

Whisper 的 encoder 做声学建模（语言无关），**decoder 做语言建模**。
泰语微调把 decoder 往泰语上拽；decoder 层数越少，容量越小，
**留给其他语言的余地就越少**。所以：

| 架构 | decoder 层数 | 泰语速度 | 英语/code-switch 保留 |
|---|---|---|---|
| Whisper medium | 24 | 慢 | **最好** |
| large-v3-turbo | 4 | 快 | 差 |
| distil-large-v3 | ~2 | 最快 | 最差 |

`typhoon-whisper-turbo` 被官方标成「泰语专用、不为英语设计」，
**根因就是 4 层 decoder**，不是训练数据的选择。

jason 的实际场景是**泰国同学说泰语时夹英文技术词**，
所以「英语保留」不是可选项，是需求。

#### 候选表

| 候选 | 架构 | 参数 | 许可 | 泰语指标 | decoder |
|---|---|---|---|---|---|
| **Thonburian medium** | Whisper medium | 764M | Apache-2.0 | WER 7.42 | **24 层** |
| **Thonburian distil-large-v3** | 蒸馏 large-v3 | 809M | Apache-2.0 | **WER 6.82** | ~2 层 |
| **typhoon-whisper-turbo** | large-v3-turbo | 809M | MIT | 未公布可比数字 | 4 层 |
| Thonburian large-v3 | Whisper large-v3 | 1540M | Apache-2.0 | WER 6.59 | 32 层 |
| typhoon-whisper-large-v3 | Whisper large-v3 | 1550M | MIT | 未公布可比数字 | 32 层 |
| typhoon-asr-realtime | NeMo FastConformer | — | — | CER 0.0984 | **要 Python/NeMo，出局** |
| 原版 whisper large-v3 | Whisper | 1540M | MIT | 最差 | 32 层 | 

⚠️ **两家的数字不可直接横比**：Thonburian 报的是 Common Voice 13 + Deepcut
分词的 WER，typhoon 报的是 Gigaspeech2 / TVSpeech / Fleurs 的 CER。
口径不同，**必须在自己的语料上重测才能横比**——这正是 M0 的教训。

**两家都没有公布 code-switch 表现**，所以「夹英文时谁更好」是纯经验问题，
只能测。

#### C1 要测的三个（都是 ~0.8B，同一条转换流水线，边际成本很低）

1. **Thonburian medium** —— 24 层 decoder，英语保留的最优候选
2. **Thonburian distil-large-v3** —— 同尺寸下泰语 WER 最好（6.82）
3. **typhoon-whisper-turbo** —— 泰语训练数据最多（11000 小时）

三个都量化到 q5/q8，测泰语纯句 + **泰英夹杂句**两组。
如果 medium 的英语保留明显更好而泰语差距不大，它就是答案。

转换路径：`whisper.cpp/models/convert-h5-to-ggml.py` 把 HF 格式转 GGML，
再用 `build/bin/quantize` 量化。whisper.cpp 已构建（HEAD `7de8dd78`，
`build/bin/` 下有 `main`/`quantize`/`whisper-bench`）。

`CLAUDE.md` 写了「Whisper 不做主链路」——那条针对的是中文 CER，
**主链路仍然是 SenseVoice**，用 whisper 系模型跑泰语不违背它。

### 要测什么（沿用 M0 的口径，便于横比）

| 指标 | 为什么要 |
|---|---|
| 泰语 CER | 能不能用的唯一判据 |
| 模型体积 | 决定下载体验，`medium` ≈ 1.5 GB / `large-v3` ≈ 3 GB |
| 冷启动 | 决定要不要常驻。SenseVoice 是 0.2s 所以不用常驻，whisper 未必 |
| RSS 峰值 | M1 预算 ≤2 GiB，**large-v3 很可能直接超预算** |
| RTF | 能不能接受 |

至少测 `small` / `medium` / `large-v3` 三档，找到「够用的最小档」。

### ⚠️ 风险：没有泰语真实语料，CER 算不出来

这是本计划最大的窟窿，得先说清楚：

- `say -v Kanya` 合成的音频**不能用来算 CER**。TTS 没有口音、没有语速
  变化、没有口头语、没有环境噪声，跑出来的数字会**显著优于真实表现**，
  拿它做选型会选错档位（很可能误判 `small` 够用）。
- 它只能用来做**冒烟测试**：验证「whisper 确实吐泰文而不是乱码」、
  验证进程调用链通了。这个价值是有的，但仅此而已。

**所以选型分两步：**

- **C1（现在能做）**：构建 whisper.cpp、转换/量化模型、用合成音频冒烟，
  建立**受控环境下的性能基线**。

  ⚠️ v1 在这里写过「这四项与语料真实性无关，现在测就是准的」，**这是错的**。
  只有**模型体积**与输入无关。RTF 受音频长度、VAD 分段、解码参数影响；
  RSS 峰值受音频长度和分段方式影响；冷启动受文件缓存冷热、首次 mmap、
  Metal shader 初始化影响。所以 C1 的数字是「基线」不是「结论」，且必须写明
  测量条件：冷/热缓存、音频长度档（10s / 30s / 5min）、线程数、解码参数固定。

- **C2（需要 jason 提供）**：真实泰语语料，才能算 CER、定档位。

在 C2 的语料到位之前，**ADR-0004 只写到「候选与性能基线」，不下最终结论**。
不要用合成语料的数字冒充实测结论——M0 的教训就是「单样本得出的准确率结论
不可靠」，这里连样本都是合成的。

### 语料要求（v1 的「5–10 段」不够）

5–10 段 × 10–30 秒总共不到 3 分钟，只够初筛，不足以支撑产品级结论。
应尽量覆盖：男/女声、不同说话人、语速快慢、安静/嘈杂环境、泰英
code-switch、数字与人名地名、短指令与长句、内置麦克风与蓝牙 HFP。

**泰语 CER 的算法也要先定死**，否则数字没有可比性：Unicode 规范化用
NFC；泰语有组合字符，**按 code point 算 CER 会给出误导性数字，应按
字素簇（grapheme cluster）计**；空格与标点是否计分要明确；英文片段
大小写如何处理。至少同时报 CER 和人工可用性评价。

## 4. 阶段 D：模型按需下载

jason 2026-08-22 拍板走**方案 A**：主包保持 241 MB，第一次切到泰语时再下载。

### 🔴 首先：不能下到 `vendor/`（v1 的阻断错误）

`main.rs::vendor_root()` 在打包运行时解析到：

```
AgentEar.app/Contents/Resources/vendor
```

往那里写下载的模型会同时踩四个坑：**破坏 app 的代码签名封印**；
`/Applications` 下普通用户可能无权写；`scripts/bundle.sh` 每次重建会
删掉整个 bundle；升级 app 时 bundle 被整体替换，几百 MB 的模型凭空消失。

必须把两个概念拆开：

| | 位置 | 属性 | 装什么 |
|---|---|---|---|
| `bundled_vendor_root()` | `…app/Contents/Resources/vendor` | **只读**，随包发布 | SenseVoice 权重 + `llama-funasr-sensevoice` |
| `downloaded_models_root()` | `~/.agentear/models/` | **可写**，跨升级保留 | 按需下载的泰语模型 |

放 `~/.agentear/models/` 而不是 `~/Library/Application Support/`：
和现有数据根一致（`AGENTEAR_DATA` 可覆盖），用户已经知道去哪找。
`AGENTEAR_VENDOR` 保持原义——**只覆盖随包资源，不参与产品数据的生命周期**。

### 下载协议（v1 的 `.part → SHA → rename` 远远不够）

那三步只保证「最终文件不出现半截内容」，没解决可恢复下载，也不是完整事务。

**必须处理的失败模式**：DNS/TLS/代理/断网/超时；HF 的重定向与 LFS/CDN 行为；
HTTP 4xx/5xx、限流、**把错误页当模型存下来**；`Content-Length` 缺失或截断；
磁盘空间不足（`.part` 与最终文件会同时占用）；`.part` 与最终文件**必须同一
文件系统**否则 rename 不原子；校验后 rename 前被杀；rename 后父目录未 fsync
就断电；重复点击或多进程同时下载；目录冒充文件、符号链接。

**「能恢复」要么真做，要么别写。** 真做需要 HTTP Range、检查服务端是否接受、
校验 `Content-Range`/ETag、远端变了要丢弃旧 `.part`、服务端返 200 而非 206
时从头覆盖。**第一版就写「失败后可安全重试（重新下载）」**，不写「断点续传」。

提交协议（对齐 `store.rs` 的思路）：

1. 在可写模型目录建唯一临时文件
2. 对这个模型上安装锁（挡住重复点击与多进程）
3. 流式下载，限制最大字节数
4. `flush` + `sync_all`
5. 校验长度与 SHA-256
6. 原子 rename
7. fsync 父目录
8. 启动时清理遗留 `.part`
9. **加载冒烟一次**——SHA 对不等于 whisper 能加载它

### 状态机（v1 的「失败退回 Auto」太粗）

```
NotInstalled → Downloading → Verifying → Installed
                   ↓             ↓
            RetryableFailure   Corrupt / Incompatible / InsufficientDisk
```

**关键语义：模型安装成功并通过加载冒烟之后，才把 `asr_lang` 提交为 `Thai`。**
否则用户会得到一个「菜单显示已选泰语、实际不能转写」的状态。
还要定义：下载中退出后重启显示什么；转写进行中切换语言是否影响当前任务；
离线时选泰语的提示；删除/重装模型的入口；进度如何从后台线程安全送到主线程。

### 从哪下

泰语模型来自 HF（`typhoon-ai/*` 或 `biodatlab/*`，见 §3）。
**GGML 需要自己转换**，所以还要决定：是我们转好后托管一份（省用户事，
但要有分发位置和许可合规），还是让用户下 HF 原始权重后本地转换
（要背 Python 转换脚本，与「不背 Python 运行时」冲突）。
**倾向前者**——转好的 GGML 放 GitHub Release，URL 与 SHA-256 随版本固化。
许可上 MIT / Apache-2.0 都允许再分发，但**必须附 NOTICE 与来源说明**。

**这是一次性的、用户显式触发的下载，不违背「录音和转写不经过第三方服务器」**
——那条约束针对的是音频数据外流，不是取模型。README 要写明白，
免得日后被当成违反隐私承诺。

## 6. 需要 jason 决定 / 提供的东西

1. **🔴 待拍板：泰语专用模型不认英语，接受吗？**
   `typhoon-whisper-turbo` 是泰语专用、明确不为英语设计。
   如果泰国同学会中英泰混着说，这个模型在英文片段上会退化。
   备选是精度略低但可能更宽容的通用 whisper，代价是体积翻倍、泰语更差。
   **这个答案决定 C1 测哪几个模型。**
2. **泰语真实语料**（要求见 §3）。没有它，CER 测不了，
   泰语档只能算「能出泰文字」而不能算「准确率可接受」。

   ⚠️ **C1 跑完后这条的重点变了。** 纯泰语朗读的准确率已经用公开的
   FLEURS 测出来了（ADR-0004 §4），不必再靠自采语料。**真正缺的是
   code-switch**——FLEURS 是朗读式新闻语料，没有夹英文，而夹英文技术词
   正是 jason 的实际场景。

   所以跟泰国同学要语料时，**必须包含夹英文技术词的句子**，这是唯一
   能填上这个缺口的东西。

   但**不要只采困难样本**：按实际使用分布分层，常规清晰语音也要有。
   只采难例会引入选择偏差，而且清晰真人语音仍能暴露 TTS 覆盖不到的
   声学差异。
3. **泰文 UI 文案的母语校对**——阶段 A 的验收项。

## 7. 计划外但应纳入的事项（评审补充）

- **ASR backend 抽象**要先于泰语接入，避免 `if Thai {...} else {...}`
  散落在主流程里
- **转写任务启动时冻结 backend 配置**，防止录音中途切换导致语义不确定
- whisper 子进程的**取消 / 超时 / 崩溃 / OOM / 退出码**处理
- **并发限制**：两个大模型同时跑很容易破 2 GiB 预算
- 配置写盘失败时，菜单显示已切换但重启丢失——需要反馈
- 自动化测试**禁止真实联网**，用本地 HTTP fixture 测重定向、截断、校验失败
- VoiceOver / accessibility label、泰文字体 fallback
