## 0. 一个必须先讲清的结论（**条件式**）

**如果**那支录音笔是一个普通的 USB 大容量存储（MSC）设备，**那么**它和「实时」就是互斥的，不要试图用一个方案覆盖两者。

理由：MSC 形态的录音笔在构造上是 store-and-forward 设备——录音时它自己的 MCU 独占 flash，只有插上主机、枚举成 U 盘之后外部才读得到文件。这种情况下你无法一边让它录、一边把数据流出来。

> ⚠️ **但这个前提尚未验证，机器还没到手。** 有几种情况会推翻上面的结论，必须在 1.0 节的刻画清单里逐条排除：
> - 它可能同时支持 **USB Audio Class**（插上就是一个 USB 麦克风，那就直接能实时）
> - 它可能有**耳机/line-out 口**——从这里接一根线到 Mac 或 ESP32 的 ADC，就绕过了全部 USB 问题，这是最省事的实时方案
> - 它可能支持**边充电边录音**并在插着的时候仍然写文件
> - 拆开之后可能有可用的板载测试点或内部麦克风信号
>
> **在刻画完成之前，不要冻结接入层架构。**

在「就是普通 MSC」这个最可能的假设下，接入层是**两条独立的路径**，不是一条：

| | 路径 A：批量归档 | 路径 B：实时对话 |
|---|---|---|
| 场景 | 会议、讲座、长录音、事后回顾 | 随口说个 idea、和助理对话 |
| 硬件 | 爱国者录音笔 + 坞站 | 流式麦克风（Mac 内置 / 手机 / ESP32-S3+MEMS） |
| 时延 | 分钟～小时级 | 亚秒级 |
| 传输 | HTTP 分块上传 | WebSocket 流 |
| ASR | 可用高精度离线模型 | 必须 Fun-ASR-Nano 流式 |
| 双工 | 无意义 | 半双工打断 |

README 里「实时的收到我的录音数据」和「用那支爱国者录音笔」这两条,**指向的是两个不同的子系统**。混在一起设计会两头不讨好。

## 1. 路径 A：录音笔怎么把数据弄出来

### 1.0 录音笔到手当天必须做的刻画（**先于一切硬件设计**）

这份清单的结果会决定 1.1–1.3 节里哪个方案还成立。**没做完之前不要买任何配件。**

| # | 测什么 | 怎么测 | 影响 |
|---|---|---|---|
| 1 | USB 描述符 | 插 Mac，`system_profiler SPUSBDataType` | 是纯 MSC？还是复合设备带 USB Audio Class？ |
| 2 | 插着能否录音 | 插上后按录音键 | 决定「实时互斥」是否成立 |
| 3 | 文件格式 | 看扩展名 + `file` + 十六进制头 | WAV / MP3 / 私有格式；能否直接喂 ASR |
| 4 | 文件关闭行为 | 录音中途拔出 | 会不会留下损坏/半截文件；关系到 3.3 的去重安全 |
| 5 | 文件系统 | `diskutil info` | FAT32？exFAT？脏位处理 |
| 6 | 时间戳可信度 | 对比文件 mtime 与真实时间 | 大概率是错的，见 3.4 |
| 7 | line-out / 耳机口 | 有没有物理接口，输出电平 | **有的话就是最省事的实时方案** |
| 8 | 拆机可行性 | 螺丝还是卡扣，PCB 是否有测试点 | 决定深度改造是否可能 |
| 9 | 边充边录 | 插充电宝试 | 影响坞站设计 |

### 1.1 关于 ESP32 方案的一处硬伤

jason 的设想是「加一块 ESP32，读取它的存储，自动上传」。方向对，但**芯片选错了**：

要读录音笔的 flash，ESP32 必须做 **USB Host**（录音笔是 USB Device）。而：

- **ESP32（经典款）**：完全没有 USB 外设，只有 UART 桥接芯片。**做不了。**
- **ESP32-C3**：USB 只支持 Device 模式。**做不了。**
- **ESP32-S2 / ESP32-S3**：有 USB-OTG，可以跑 USB Host + MSC。**这才是能用的型号。**

ESP-IDF 官方有 USB Host MSC 驱动，技术上可行。但要自己写：USB 枚举 → MSC 传输 → FAT32 解析 → 大文件分块读 → WiFi 连接 → 断点续传上传。**这是一坨相当可观的 C 固件**，而且 ESP32-S3 只有 512KB SRAM，读 100MB 的 WAV 必须精细地流式分块，缓冲区管理会很难受。

### 1.2 坞站方案对比

如果确实要做「插上就自动同步」的坞站，候选不止两个：

| 方案 | 成本 | USB Host | 工程量 | 真实风险 |
|---|---|---|---|---|
| **Mac 直连 + launchd** | ¥0 | 系统自带 | **~20 行 shell** | 需要人把笔插到 Mac 上 |
| 手机 OTG 中转 | ¥10（转接头） | 系统自带 | 一个 App/快捷指令 | iOS 侧受限，Android 可行 |
| **Pi Zero 2 W** | ~¥120 | 内核自带 | shell + udev | 见下方「被低估的部分」 |
| ESP32-S3 | ~¥50 | **自己写 MSC 驱动** | 数百行 C，调 USB 栈 | 512KB SRAM，大文件流式缓冲难 |
| 旧路由器刷 OpenWrt | ¥0（有闲置的话） | 内核自带 | 类似 Pi | USB 供电可能不足 |

**上一版本这里只对比了 ESP32-S3 和 Pi，并且低估了 Pi 的工作量。** Pi 方案「~20 行 shell」只覆盖了顺利路径，实际还要处理：

- **脏 FAT**：录音笔非正常拔出留下的脏位，`mount` 会拒绝或只读挂载
- **不安全拔出**：用户在同步中途拔走笔
- **自动挂载的安全性**：自动 mount 未知 U 盘本身是有攻击面的
- **WiFi 凭据管理**：headless 设备的配网
- **服务加固**：断电重启后自恢复、日志轮转、SD 卡磨损
- **现场恢复**：坞站出问题时没有屏幕，怎么排查

算上这些，Pi 方案是「一个周末」而不是「20 行」。ESP32-S3 则是「几周」。

**建议：先做 Mac 直连（¥0），坞站往后放。** 理由见 1.3。真要做坞站时选 Pi Zero 2 W——坞站本来就插电，ESP32 的低功耗优势用不上，而它的固件成本是实打实的。

真正需要 ESP32-S3 的是路径 B（要电池供电、要小），见第 2 节。

### 1.3 完全不改造的兜底方案

在坞站做好之前，路径 A 可以先用**最土的办法**跑通全链路：录音笔插 Mac，一个 `launchd` 监听挂载事件，脚本 rsync 到 `raw/`。

**这个方案零成本、当天能跑，而且它验证的是整条下游链路（去重、落盘、转写、路由）——那才是真正的复杂度所在。** 坞站只是把「手动插 Mac」换成「插一个盒子」，属于体验优化，不是核心价值。

**强烈建议先做这个，坞站往后放。**

## 2. 路径 B：实时流

### 2.1 v1 用 Mac 内置麦克风

README 自己写了「先完成连接我的手机的或者是 MacBook 的」。这是对的：**零硬件、零传输协议，直接验证 ASR 这个最大未知数**。

### 2.2 v2 才考虑独立硬件

如果要一个能随身带的实时收音设备，**这时候才轮到 ESP32-S3**——但不是用来读录音笔，而是**直接当录音设备**：

- ESP32-S3 + I2S MEMS 麦克风（INMP441 或 ICS-43434，~¥10）
- 采 16kHz/16bit 单声道 PCM，直接 WebSocket 推给 Mac
- 不落本地存储，不需要 USB Host，**绕开了 1.1 节的全部难点**

功耗估算：ESP32-S3 + WiFi 持续发送约 100–150mA，1000mAh 电池约 7–10 小时。够用一天。

**这条路比改造录音笔更接近你真正想要的东西**（实时、双工），而且工程量更小。录音笔那条路，本质上只适合做归档。

## 3. 传输协议

### 3.1 先排除几个选项

- **蓝牙：不适合批量同步。** BLE 的有效吞吐高度依赖版本、MTU 协商和两端协议栈，但在任何配置下都比 WiFi 低一到两个数量级，传几十 MB 的录音在可用性上站不住。BT Classic SPP 更快些但 macOS 侧支持很难受。A2DP 是有损压缩且方向反了（是往音箱推的）。**蓝牙保留给配对和控制信令，不承载数据。**
- **FTP：能用但没必要。** 无像样的鉴权，Mac 上还得额外跑一个 FTP 服务，不如直接 HTTP。

### 3.2 定下来的方案

Mac 上跑一个常驻 daemon，暴露两个端点，通过 **mDNS/Bonjour** 广播为 `agentear.local`（macOS 原生支持，设备侧零配置发现）：

```
POST  /ingest        分块上传，用于路径 A（批量文件）
WS    /stream        16kHz PCM 流，用于路径 B（实时）
```

### 3.3 提交协议（commit protocol）

「先 ACK 再删」是**必要但远不充分**的。崩溃可能发生在「文件已 fsync」但「目录项或清单尚未持久化」之间，那时文件在磁盘上却无法被可靠发现。所以要定义完整的提交序列：

```
1. 服务端生成高熵 session_id（不接受客户端提供的），
   以 O_EXCL 创建 raw/.tmp/<session_id>        ← O_EXCL 保证不会撞上并发会话
2. 每个分块校验 offset + 长度 + 分块 hash，追加写入
3. 全部收齐后校验最终 content hash
4. fsync(临时文件)
5. rename() 原子改名到  raw/audio/<content_hash>
6. fsync(raw/audio 目录)          ← 少了这步，目录项可能丢
7. 在同一条事务里分配接收序号 + 写入清单，然后 fsync 清单及其目录
8. 此时才返回最终 ACK: COMMITTED
```

**几个必须说清的细节：**

- **`session_id` 由服务端生成且高熵**。让客户端指定等于给了它覆盖别人临时文件的能力。配合 `O_EXCL`，创建冲突直接失败而不是静默复用。
- **分块 ACK 的语义要写死**：分块 ACK **不承诺持久化**，只表示「这段字节已收到并通过校验」。守护进程崩溃后，未 COMMITTED 的临时对象一律作废重传——不要试图从半截临时文件恢复偏移量，除非分块本身也 fsync 了（不建议，太慢）。设备侧必须把「分块 ACK」当作可丢失的。
- **并发重复上传不能只靠内容文件收敛**。两个会话同时传同一份录音，第 5 步的 rename 确实会收敛到同一个路径（后者覆盖前者，内容相同所以无害），但**清单写入和接收序号分配必须是原子的**，否则会出现两条清单记录或两个序号。用一个带唯一约束的嵌入式数据库（SQLite 之类）承载清单和序号，比手写文件更容易保证。
- **接收序号的持久化状态**是排序权威（见 3.6），它和清单必须一起持久化，不能是内存计数器。

**设备侧不要在收到 COMMITTED 的瞬间删除原文件**，而是标记为已同步，由后续的 GC 在一个保留窗口（比如 7 天或容量水位触发）之后才真正删。这样即使服务端事后发现数据有问题，还有一次补救机会。

### 3.4 其余约束

1. **幂等**：上传带 `(device_id, file_id, content_hash)`。重复插坞站不能重复导入，服务端按 content hash 做内容寻址去重。并发的重复上传要靠第 5 步的 rename 天然收敛（同一 hash 改名到同一路径）。
2. **断点续传**：分块 + offset。50MB 文件传到一半 WiFi 断了不能从头再来。
3. **鉴权不能用静态明文 token。** 明文 HTTP 上的固定 token 会被同网段嗅探、重放，也容易泄漏进日志。

   **默认方案是固定证书的自签名 HTTPS/WSS**（设备侧 pin 住服务端证书指纹）。理由：这是一个**隐私优先**的项目，而 HMAC 只做**认证**、不做**加密**——录音内容仍然在局域网上明文传输，任何同网段设备都能听到。对一个「不想让数据裸奔」的项目，这是自相矛盾的。

   HMAC 作为 ESP32 这类 TLS 开销吃不消的设备的降级选项，参数必须写死：

   | 参数 | 取值 |
   |---|---|
   | 签名内容 | `method + path + body_hash + nonce + timestamp + counter` |
   | nonce | ≥ 16 字节，密码学随机 |
   | 时间戳容差 | ±5 分钟（设备时钟不可靠，见 3.7，容差不能太紧） |
   | counter | **必须跨重启持久化**，否则 ESP32 断电后从 0 开始，重放窗口大开 |
   | 重放缓存保留 | ≥ 时间戳容差窗口的 2 倍 |
   | 密钥下发 | 带外配置（烧录/配网时写入），不走待鉴权的信道 |
   | 密钥轮换 | 支持同时接受新旧两把密钥的过渡期 |

   - **WebSocket 的 upgrade 握手同样要鉴权**，不能只保护 HTTP 端点
   - mDNS 是可欺骗的，**不能把「发现了 agentear.local」当作信任依据**
4. **raw 先落盘再处理**：`COMMITTED` 之后才允许开始转写/分类。这是 README「先存后分流」原则的执行点。

### 3.5 去重的一个陷阱：文件还在被写

**对一个仍在被写入的文件算 content hash 是错的**——部分内容的 hash 不等于最终 hash，会导致同一份录音被当成两个不同对象导入两次。

坞站/导入侧在 hash 之前必须先确认文件**稳定**：

- 连续两次扫描之间 size 未变化
- 没有临时文件扩展名（各家录音笔在录制中的命名约定不同，1.0 节第 4 项要测出来）
- 设备未处于录音状态

### 3.6 排序权威

设备时钟不可信（见 3.7），所以**排序以服务端的接收序号为准**，设备时间只作为附加字段存下来供参考。任何依赖设备时间做先后判断的逻辑都是 bug。

### 3.7 实时流的 raw 语义（**路径 B 专用，和文件路径规则不同**）

前面 3.3–3.6 全部是**文件形状**的：有明确的开始、结束、最终 content hash。WebSocket 上的 PCM 流**没有这些边界**，直接套用会得到一个永远无法 COMMIT 的对象。所以路径 B 需要单独定义。

**一个 raw 对象 = 一个定长时间片。**

```
session_id（一次连接） + segment_index（单调递增）
  ↓
每 60 秒（或连接关闭时）切一个 segment
  ↓
segment 关闭时计算 content hash，走 3.3 的提交协议后半段
  ↓
raw/audio/<content_hash>，清单里记 (session_id, segment_index)
```

### ⚠️ 路径 A 也必须分段（M0 实测结论）

**长音频不能整文件喂给 ASR。** M0 实测 RSS 随音频长度线性增长约 **0.56 MB/秒音频**：

| 音频时长 | 峰值 RSS |
|---|---|
| 10 min | 1.771 GiB ✅ |
| 30 min | **2.452 GiB ❌ 爆预算** |
| 60 min（外推） | 3.42 GiB |

**导入侧必须按时间窗切分后逐段转写，单段 ≤5 分钟**（实测 1.627 GiB，余量 19%）。一个 3 小时的会议录音整喂进去会吃掉 7+ GiB。

注意这是**转写阶段**的切分，不改变 raw 存储——路径 A 的 raw 对象仍是完整原文件，切分只发生在喂给 ASR 时。详见 `docs/benchmarks.md` §2。

---

**为什么用定长时间片而不是 VAD 语音段切分**：VAD 会切错，而 raw 存在的意义正是「即使 VAD 切错了，原始记录仍然忠实」。用 VAD 边界定义 raw 对象等于让 raw 依赖一个它本该兜底的组件。**时间片只依赖时钟递增，不依赖任何模型判断。**

**ASR 不等待 fsync——用 tee，不用串行。**

如果每一帧都要等落盘才能喂给 ASR，实时性直接没了。正确做法是把 PCM 流分叉：

```
        ┌→ 持久化写入器：追加到当前 segment，周期性 fsync
PCM 流 ─┤
        └→ ASR 喂入器：内存直通，不等待磁盘
```

**代价必须明说：这引入了一个有界的数据丢失窗口。** 崩溃时会丢掉「最后一次 fsync 之后」的音频。所以：

- **fsync 周期要定死**（建议 1 秒或每 64 KB，取先到者），这个数字**就是你能接受的最大丢失量**，必须显式写进配置而不是隐含在实现里
- 这和路径 A 的「零丢失」保证是**不同等级**的。文件导入可以做到不丢，实时流做不到——这是物理约束，不是实现偷懒
- 文档和代码里不要用同一个词描述两种保证

**流式转写结果的状态机**：从尚未 COMMITTED 的 segment 产生的转写是 **provisional**，segment 提交成功后才转为 **committed**。下游路由（建任务、写 knowledge base）**只消费 committed 的转写**，避免因崩溃产生幽灵任务。实时显示给用户看的可以是 provisional。

**排序**：路径 B 的顺序由 `(session_id, segment_index)` 决定，不用 3.6 的全局接收序号——流内部的顺序是确定的。跨路径的全局排序仍以服务端接收序号为准。

### 3.8 时钟问题

ESP32 和多数廉价录音笔**没有带电池的 RTC**，断电后时间归零。所以：

- 设备上报的时间戳只当**提示**，不当权威
- 服务端以**接收时间**为准，设备时间存为附加字段
- 录音笔的文件名/FAT 时间戳同理——爱国者这种设备的时间大概率就是错的

## 4. 建议的落地顺序

```
第 1 步（零硬件，验证最大风险）
  Mac 麦克风 → raw/audio 落盘 → Fun-ASR-Nano
  产出：asr-selection.md §5.1 的完整基准表
  ↓
第 1.5 步（录音笔一到手就做，不要等）
  执行 §1.0 的刻画清单
  ← 这一步的结果可能推翻 §0 的「实时互斥」前提，
    进而推翻整个坞站方案。放得越晚，返工越贵。
  ↓
第 2 步（打通下游，仍然零硬件）
  raw/ → 标签识别 → routes/ → idea/task/knowledge base
  ↓
第 3 步（土办法接入录音笔）
  launchd 监听挂载 → 稳定性检测 → 导入 raw/
  ↓
第 4 步（协议化）
  抽出 HTTP /ingest + 鉴权 + 提交协议，让接入源可替换
  ↓
第 5 步（硬件，二选一或都做）
  A: Pi Zero 2 W 坞站      B: ESP32-S3 + MEMS 实时麦
```

**第 1.5 步是插进来的**：原先把录音笔刻画放在最后，但它是**能推翻架构的高风险未知项**——如果那支笔根本不是普通 MSC（比如带 USB Audio Class，或者有 line-out），第 3–5 步的设计就白做了。高风险项要前置。

**每一步都能独立产生价值，且第 1、2 步不需要买任何东西。**
