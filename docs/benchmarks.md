日期：2026-07-29
机器：MacBook Pro，Apple M1 Max（8P+2E），64 GB
被测：Fun-ASR-Nano q4km + `llama-funasr-cli` v0.1.9（macOS arm64 预编译，零 Python）

## 1. 模型体积：澄清 484MB vs 800MB 之谜

**两个数字都不对，模型是拆成两个 GGUF 的。**

| 文件 | 实测 |
|---|---|
| `funasr-encoder-f16.gguf`（编码器 + adaptor） | 447.6 MiB |
| `qwen3-0.6b-q4km.gguf`（Qwen3-0.6B 解码器） | 461.8 MiB |
| `fsmn-vad.gguf`（**独立 HF 仓库**，需单独下） | 1.6 MiB |
| **合计** | **910.9 MiB** |

「484 MB」是**解码器单文件的十进制表示**（461.8 MiB × 1.048576 = 484.2 MB）。官方 README 写着「Pair any with `funasr-encoder-f16.gguf` (470 MB)」。

**修正 `asr-selection.md` 的两处错误**：
1. 权重实际约 **910 MiB**，接近原估算（484 MB）的两倍
2. 「内置 FSMN-VAD」不准确 —— 是**运行时**支持，VAD 模型在 `FunAudioLLM/fsmn-vad-GGUF`，要单独下载

**量化档位**：官方三档 CER 差异 <0.1%（q4km 8.35% / q5km 8.25% / q8_0 8.30%），选最小的 **q4km**。

## 2. 性能：**RSS 随音频长度线性增长，30 分钟即爆预算**

这是本轮最重要的发现。

| 音频时长 | 峰值 RSS | RTF | VAD 段数 | ≤2 GiB |
|---|---|---|---|---|
| 31.72s | 1.465 GiB | 0.032 | 2 | ✅ |
| 119.64s | 1.529 GiB | 0.062 | 19 | ✅ |
| **5 min** | 1.627 GiB | — | — | ✅ |
| **10 min** | 1.771 GiB | — | — | ✅ |
| **30 min** | **2.452 GiB** | 0.074 | 539 | ❌ **超预算 23%** |

**增长率约 0.56 MB / 秒音频。** 外推：60 分钟 → **3.42 GiB**，120 分钟 → **5.40 GiB**。

### 缓解方案（已验证有效）

**长音频必须分段送入，不能整文件喂。** 单段 ≤10 分钟即可压在 2 GiB 内；**建议 5 分钟**（1.627 GiB，余量 19%）。

> ⚠️ 这是一条**架构级约束**，不是调优建议。`ingest-design.md` 的路径 A（录音笔长录音，小时级）**必须**在导入时按时间窗切分后逐段转写，否则一个 3 小时的会议录音会吃掉 7+ GiB。
>
> 路径 B（实时流）天然受 §3.7 的定长时间片保护，不受影响。
> M1（快捷键录音，通常几十秒到几分钟）不受影响。

### 其余性能结论

- **RTF 0.032–0.074**，即 13–31 倍实时，**余量巨大**，且随长度增长而略降但不显著
- **30 分钟连续跑无崩溃、无异常**（539 个 VAD 段）
- **单二进制 6.7 MB**，7 个可执行文件全包，零 Python 依赖 —— 符合常驻守护进程要求

### ⚠️ 冷启动 10.5 秒

首次 11.45s vs 热运行 1.0s，差值即载入 910 MiB 权重的时间。

`milestones.md` 里 M1 写的「冷启动到可录音 < 3 秒」**按当前方案做不到**。已改为：
- 「常驻后按键到开始录音 < 200ms」
- 「开机加载完成 < 15s，且加载中状态在菜单栏可见」

### Metal 未被使用

`ggml_metal_device_init` 正确识别 M1 Max（MTLGPUFamilyApple7），但计算缓冲全在 CPU（`CPU compute buffer 1203 MiB` / `MTL0 0.00 MiB`）。CLI 未暴露 `-ngl`。

**不需要优化** —— CPU 已达 13–31 倍实时。附带好处：**GPU 完全空闲，M2 跑 LLM 时不会和 ASR 抢**。

## 3. 准确率：CER 24.75%，但这个数字有重要限定

### 3.1 限定条件

sample02 的参考文本是 **jason 口述 README 的另一个 ASR 转写结果**，不是人工逐字稿。它自身带明显错误（`mark book`→MacBook、`row`→raw、`二四小时`→24小时）。

**所以下表测的是「两个 ASR 系统的分歧率」，不是准确率。真实 CER 应低于此数。**

| 口径 | CER |
|---|---|
| 原始（含语气词） | **24.75%** |
| 剔除语气词/助词 | **22.39%** |

（Fun-ASR-Nano 还多转出了参考文本里没有的开场白「我们来测试一下这个录音功能」，那是真实说了但没写进 README 的，计算时已剔除。）

### 3.2 逐术语人工判定

在两边不一致处逐个判断谁对：

| 实际词 | 参考（另一 ASR） | Fun-ASR-Nano | 判定 |
|---|---|---|---|
| MacBook | `mark book` ✗ | `妈的book` ✗ / `MacBook` ✓ / `macbook` ✓ | **Nano 胜** |
| knowledge base | `knowledge base` ✓ | `闹铃是base` ✗ | **参考胜** |
| 24小时 | `二四小时` ✗ | `二四二` ✗✗ | 参考略胜 |
| raw | `row` ✗ | `road` ✗ | 都错 |
| Mac mini | `mark mini` ✗ | `mark mini` ✗ | 都错 |
| 爱国者 / 闲鱼 / 录音笔 / wifi / idea / report / 8G | ✓ | ✓ | 都对 |

**结论：中文口语部分两边都不错；中英混杂的技术术语两边都会翻车，水平大致相当**（6 个硬术语各对 1 个）。

### 3.3 这对 AgentEar 是个真问题

jason 的使用场景**恰恰全是技术术语**。换 ASR 模型未必能解决——这是中英混杂的固有难点。

**建议：把「术语纠错」列为 M2 标签识别层的明确职责**，用本地 LLM 结合上下文把 `road目录`→`raw目录`、`闹铃是base`→`knowledge base` 纠回来。这比换 ASR 划算，且 LLM 本来就要在链路里。

### 3.4 `/sil` token 泄漏

`--chunk` 模式下输出混入 `/sil` 特殊 token（如 `他在讲什么？/sil/sil/sil/sil能尝尝...`）。**M1 实现必须做后处理过滤**，否则会粘进用户剪贴板。

### 3.5 配置对结果影响巨大（sample01，无 ground truth）

| 配置 | 输出 |
|---|---|
| `--vad` | 他在讲。尝尝大香菇。 |
| 无 VAD | 这个也是，你看这个，他在从我这。 |
| `--chunk 10` | 你听这个，他在讲老庄。the先尝尝大香鸡来呀。/sil |
| `--chunk 5` | 你听这个，他在讲什么？/sil/sil/sil/sil能尝尝大香鸡了呀。/sil |

sample01 是 -30.8 dB 的远场录音，处在模型能力边界上。**VAD 模式是默认且最稳的选择。**

## 3.6 横向对比（2026-07-29 补做）

同一段语料（sample02，jason 口述 README，119.64s），同一台 M1 Max，同一个 VAD。

| 模型 | 权重 | RSS(2min) | **RSS(30min)** | RTF | CER | CER(剔语气词) | 术语命中 | 标点 |
|---|---|---|---|---|---|---|---|---|
| Fun-ASR-Nano q4km | 910 MiB | 1566 MB | **2.45 GiB ❌** | 0.062 | **24.75%** | **22.39%** | 9/13 | ✅ |
| **SenseVoiceSmall q8** | **242 MiB** | **419 MB** | **1.27 GiB ✅** | **0.033** | 25.08% | 22.94% | **10/13** | ✅ |
| Paraformer q8 | 226 MiB | 315 MB | 1.25 GiB ✅ | 0.036 | 25.75% | 24.04% | 8/13 | ❌ **无标点** |
| 参考（另一 ASR 的输出） | — | — | — | — | — | — | 10/13 | ✅ |

### 结论一：三者准确率在噪声范围内，但资源差 4–5 倍

CER 相差不到 1 个百分点（24.75 / 25.08 / 25.75），**单样本上无法区分优劣**。但 SenseVoice 的常驻内存只有 Nano 的 **27%**，速度快 **1.9 倍**。

### 结论二：SenseVoice 的内存基线低得多，长音频优势决定性

三个模型的增长率几乎一样（0.52–0.58 MB/秒音频），差别全在**基线**：

| 模型 | 增长率 | 预计破 2 GiB 的音频长度 |
|---|---|---|
| Fun-ASR-Nano | 0.56 MB/s | **约 16 分钟** |
| SenseVoiceSmall | 0.52 MB/s | 约 54 分钟 |
| Paraformer | 0.58 MB/s | 约 52 分钟 |

**Nano 在 16 分钟就破预算，SenseVoice 能撑到 54 分钟——差 3.4 倍。**
两者都仍需分段，但 SenseVoice 的分段窗口可以宽松得多。

### 结论三：关键术语上 SenseVoice 反超

| 正确词 | 参考 | Nano | SenseVoice | Paraformer |
|---|---|---|---|---|
| MacBook | ✓ | ✓ | ✓ | ✓ |
| **Mac mini** | ✗ | ✗ | **✓ 唯一答对** | ✗ |
| **24小时** | ✗ | ✗ | **✓ 唯一答对** | ✗ |
| knowledge base | ✓ | ✗ | ✗ | ✗ |
| raw 目录 | ✗ | ✗ | ✗ | ✗ |
| 本地模型 | ✓ | ✓ | ✗ | ✗ |
| AI / idea / report / wifi / 爱国者 / 闲鱼 / 8G | ✓ | ✓ | ✓ | ✓ |
| **命中** | 10/13 | **9/13** | **10/13** | 8/13 |

**`raw` 三家全错**（road / ro / roll）——这个词对所有 ASR 都是硬骨头，坐实了「术语纠错必须交给 M2 的 LLM」的判断。

### 结论四：「SenseVoice 即将停止维护」是错的，需更正 `asr-selection.md`

`asr-selection.md` §1 写着 SenseVoice「官方标注即将停止维护」，来源是厂商博客（funasr.com）的二手说法。**实际仓库状态与此不符：**

- GitHub `QwenAudio/SenseVoice`：**未 archive**，最后提交 2026-07-27（2 天前），8951 stars
- HF `SenseVoiceSmall-GGUF`：2026-06-21 更新，下载量 5755（高于 Nano 的 4813）

弃用风险比原文档描述的低得多。

### Paraformer 出局

**它完全不输出标点。** 对一个要把语音变成笔记/任务的产品，这是硬伤——虽然它内存最小、CER 只差 1 个百分点。

### 结论五：Qwen3-ASR-0.6B 术语最强，但 Python 运行时是硬伤

| 项 | 值 |
|---|---|
| 权重 | 960 MiB（MLX 8bit safetensors） |
| RSS（2min / 30min） | 1.18 GiB / **1.565 GiB ✅** |
| RTF | 0.029–0.034 |
| CER | 24.92% |
| 术语命中 | **10/13**（唯一答对 `knowledge base`） |
| 增长率 | **0.24 MB/s**（四家最低，破 2 GiB 需 61 分钟） |

**它在纯指标上很强**：内存增长率只有其他三家的一半，术语最好。

**但它需要 Python + MLX 运行时。** 这直接违反 `CLAUDE.md` 定的「常驻守护进程不背 Python 运行时」——Rust 守护进程要用它，只能 shell out 给 Python（等于把 Python 塞回常驻链路）或等 `mlx-rs` 成熟。**这一条足以让它出局**，除非未来出现 GGUF/纯 Rust 路径。

它错的地方也很特别：`idea`→`ID`、`report`→`日报`，而这两个词其他三家都对。

### 四模型内存增长曲线

| 模型 | 增长率 | 破 2 GiB 的音频长度 |
|---|---|---|
| Fun-ASR-Nano | 0.56 MB/s | **16 分钟** |
| Paraformer | 0.58 MB/s | 52 分钟 |
| SenseVoiceSmall | 0.52 MB/s | 54 分钟 |
| Qwen3-ASR | **0.24 MB/s** | **61 分钟** |

**Nano 是唯一一个在 30 分钟就爆预算的。**

## 3.7 选型建议：从 Fun-ASR-Nano 改为 SenseVoiceSmall

**理由不是准确率**（四家 CER 24.75–25.75%，单样本无法区分），**而是工程形态：**

1. **常驻 419 MB，是 Nano 的 27%** —— 省下的 1.1 GiB 正好留给 M2 的 LLM
2. **长音频撑到 54 分钟，Nano 只到 16 分钟** —— 差 3.4 倍
3. **单二进制零 Python**，与 Qwen3-ASR 相比是决定性优势
4. **术语命中 10/13 反超 Nano 的 9/13**
5. 原先排除它的理由「即将停止维护」**经核实不成立**

**出局理由汇总**：
- Paraformer：不输出标点，笔记类产品的硬伤
- Qwen3-ASR：Python + MLX 运行时
- Fun-ASR-Nano：内存基线过高，16 分钟即破预算

### 待补

FireRedASR2-AED 需要单独的 CrispASR 运行时，且 q4_k 权重就 918 MiB，在 ≤2 GiB 预算下大概率不可行，作为离线兜底组的候选另行评估。

Qwen2.5-Omni-3B（全模态）下载中，见 §3.8。

## 3.8 全模态模型：不建议替代 ASR，建议按需分层

jason 提出把内存预算放宽到 3–4 GiB，换取语音 + 图片 OCR 的全模态能力。**查证结果：**

| 模型 | 权重合计 | 3–4 GiB 预算 |
|---|---|---|
| **Qwen2.5-Omni-3B** | **3.4 GiB**（主体 Q4_K_M 2007 + mmproj Q8 1467） | ⚠️ 卡在边缘 |
| MiniCPM-o 4.5 | **6.1 GiB**（Q4_K_S 4579 + audio 630 + vision 1044） | ❌ 超一倍 |
| Qwen3-Omni-30B-A3B | 4bit 约 15 GiB | ❌ |
| Nemotron-3-Nano-Omni-30B | 4bit 约 15 GiB | ❌ |

（MiniCPM-o 的数字与 jason 博客 `minicpmo-omni-model-developer-guide-selection.md` 里「Int4 约需 8–12GB 内存」吻合。）

### 建议：不替代，分层

```
常驻层（始终在内存）
  SenseVoiceSmall q8   242 MiB   ← 只做语音转文字，快且省

按需层（用时加载，用完卸载）
  ├─ 本地 LLM              ← M2 的标签路由 + 术语纠错
  └─ 全模态模型  3.4 GiB    ← 截图 OCR、看图提问，真需要时才起
```

**三条理由：**

1. **常驻与按需是两种东西。** ASR 必须永远在线（要一直听），图片 OCR 是偶发的。分层后常驻开销是全模态方案的 **7%**，能力完全一样。为偶尔用的功能付永久内存租金不划算。
2. **全模态模型不是为连续转写设计的。** 它吃的是「一段音频 + 一个问题」，而路径 A 是小时级连续转写。M0 已证明 RSS 随音频长度增长，3B 模型在这条曲线上只会更陡。
3. **速度差一个数量级。** SenseVoice 是 30 倍实时 / 419 MB；3B 全模态在 M1 Max 上做转写乐观估计 2–5 倍实时，对「按键即出字」的体验差别明显。

**结论：全模态属于 M2 之后的按需层，不占 M0 的 ASR 位置。**

## 4. M0 结论

### 通过的部分

| 门槛 | 结果 |
|---|---|
| 峰值 RSS ≤ 2 GiB | ✅ **有条件通过** —— 单段 ≤10 分钟；建议 5 分钟 |
| RTF < 1.0 且有余量 | ✅ 0.032–0.074，13–31 倍实时 |
| 模型实际体积 | ✅ 已澄清，910 MiB |
| 30–60 分钟长跑稳定性 | ✅ 30 分钟无崩溃 |
| 中文口语准确率 | ✅ 可用 |

### 未完成 / 有保留的部分

- **横比未做**：Paraformer 流式、SenseVoice/ONNX、mlx-audio Qwen3-ASR、FireRedASR2 均未测。
  由于 Nano 的绝对指标已达标，横比降为**低优先级**——只有在 M1 实测中发现准确率不可接受时才需要回头做。
  （运行时已含 `llama-funasr-paraformer` 和 `llama-funasr-sensevoice` 二进制，只差模型。）
- **技术术语准确率不理想**，需 M2 的 LLM 纠错层兜底。
- **热行为/降频**未单独测量（30 分钟跑完未见性能衰减，但没做温度采样）。

### 选型状态

**Fun-ASR-Nano q4km 可以进入 M1**，但选型仍标记为**「条件锁定」**而非「绝对最优」——因为没有横比，无法断言它是最好的，只能断言它**够用且满足全部硬约束**。

### 本轮新增的架构约束（已回写 `CLAUDE.md`）

1. **长音频必须分段（≤5 分钟/段）送入 ASR** —— 路径 A 的硬性要求
2. 冷启动 10.5s，M1 验收标准已相应调整
3. `/sil` token 需后处理过滤
4. 技术术语纠错是 M2 的职责，不指望 ASR 直接出对
