# M0 基准测试结果

日期：2026-07-29
机器：MacBook Pro，Apple M1 Max（8P+2E），64 GB
语料：`20201120_103041.m4a`（2020 年安卓手机录制，31.72 秒，48kHz 立体声 AAC → 转 16kHz 单声道 WAV）

> **状态：部分完成。** 性能指标已测出，**CER 尚缺——没有 ground truth 无法计算**。见第 4 节。

## 1. 已澄清：484MB vs 800MB 之谜

**两个数字都不对，模型是拆成两个 GGUF 的。**

| 文件 | 实测大小 |
|---|---|
| `funasr-encoder-f16.gguf`（编码器 + adaptor） | 447.6 MiB |
| `qwen3-0.6b-q4km.gguf`（Qwen3-0.6B 解码器） | 461.8 MiB |
| `fsmn-vad.gguf`（**独立仓库**，需单独下载） | 1.6 MiB |
| **合计** | **910.9 MiB** |

那个「484 MB」是**解码器单文件的十进制表示**（461.8 MiB × 1.048576 = 484.2 MB）。官方 README 明确写着「Pair any with `funasr-encoder-f16.gguf` (470 MB)」。

**修正 `asr-selection.md` 的两处错误：**
1. 权重实际约 **910 MiB**，接近原估算（484 MB）的两倍
2. 「内置 FSMN-VAD」的说法不准确 —— 是**运行时**支持，VAD 模型在另一个 HF 仓库（`FunAudioLLM/fsmn-vad-GGUF`），要单独下

### 量化档位选择

官方给的三档 CER 差异在 0.1% 以内（q4km 8.35% / q5km 8.25% / q8_0 8.30%），**选最小的 q4km**，没必要为 0.1% 多背 300 MB。

## 2. 性能实测（Fun-ASR-Nano q4km）

运行时：`llama-funasr-cli` v0.1.9（macOS arm64 预编译二进制，零 Python）

| 指标 | 实测值 | 门槛 | 结论 |
|---|---|---|---|
| 峰值 RSS | **1.563 GiB**（三次运行稳定：1564/1563/1563 MB） | ≤ 2 GiB | ✅ 通过，余量约 22% |
| RTF（热，模型已在页缓存） | **0.032**（31.72s 音频耗时 1.0s，约 31× 实时） | < 1.0 | ✅ 大幅通过 |
| RTF（冷启动，含载入权重） | 0.36（首次运行 11.45s） | — | 见下方警告 |
| 二进制体积 | 6.7 MB（7 个可执行文件全包） | — | ✅ 单文件无依赖 |

### ⚠️ 冷启动 10.5 秒，与 M1 的验收标准冲突

首次运行 11.45s，热运行 1.0s，**差值约 10.5 秒就是载入 910 MiB 权重的时间**。

`docs/milestones.md` 里 M1 写的验收标准是「冷启动到可录音 < 3 秒」，**这一条按当前方案做不到**。可选对策：

- 守护进程开机即加载并常驻（本来就是设计意图），冷启动只在开机时发生一次
- 但要接受：**开机后第一次按快捷键前有约 10 秒不可用窗口**，需要在 UI 上明示（菜单栏图标显示「加载中」）
- 或者延迟到首次使用才加载，代价是第一次录音要等

**建议把 M1 的验收标准改成「常驻后按键到开始录音 < 200ms」+「开机加载完成 < 15s 且状态可见」。**

### Metal 未被使用

`ggml_metal_device_init` 正确识别了 M1 Max（MTLGPUFamilyApple7），但计算缓冲区全在 CPU：

```
CPU compute buffer size = 1203.01 MiB
MTL0 compute buffer size = 0.00 MiB
```

CLI 没有暴露 `-ngl` 之类的参数。**但 CPU 已经跑到 31× 实时，没有优化必要**，记录备查即可。这也意味着 GPU 完全空着，未来跑 LLM 时不会和 ASR 抢。

## 3. 转写输出：同一段音频，不同配置结果差异很大

| 配置 | 输出 | 耗时 |
|---|---|---|
| `--vad`（默认 maxseg 30s） | 他在讲。尝尝大香菇。 | 0.99s |
| `--vad --vad-maxseg 5000` | 他在讲。尝尝大香菇。 | 0.99s |
| 无 VAD | 这个也是，你看这个，他在从我这。 | 1.56s |
| `--chunk 10` | 你听这个，他在讲老庄。the先尝尝大香鸡来呀。/sil | 1.69s |
| `--chunk 5` | 你听这个，他在讲什么？/sil/sil/sil/sil能尝尝大香鸡了呀。/sil | 1.98s |

### 三个发现

1. **31.72 秒音频只转出十几个字。** VAD 只找到 **2 个语音段**。这段录音 `mean_volume = -30.8 dB`（相当安静），推测是远场／环境录音而非近讲，大部分时间可能确实没有清晰人声。**但这需要 ground truth 才能确认是「音频本来就没内容」还是「模型漏掉了」。**

2. **`/sil` 特殊 token 泄漏进输出**（`--chunk` 模式下尤其明显）。这是运行时的 bug 或需要后处理过滤，**M1 实现时必须处理**，否则会把 `/sil` 粘进用户的剪贴板。

3. **配置对结果影响巨大**，「大香菇」vs「大香鸡」、「他在讲老庄」vs「他在讲什么」都是同一段音频的不同解码。这说明**这段音频处在模型的能力边界上**，正是有价值的测试样本。

## 5. 当前结论

**性能维度：Fun-ASR-Nano q4km 通过。** RSS 1.56 GiB 在预算内，RTF 0.032 有巨大余量，单二进制零依赖的形态符合常驻守护进程的要求。

**准确率维度：未验证。** 在拿到 ground truth 之前，不能说 M0 通过，也不能把选型从「暂定」升级为「锁定」。

**已发现但文档里没有的问题**：冷启动 10.5 秒与 M1 验收标准冲突、`/sil` token 泄漏需要后处理。
