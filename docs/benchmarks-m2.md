## 2. 两处测量方法的错误（都是我这边的问题，值得记下）

第一轮跑出「术语纠错 100% + 标签分类 0%」，两个数字**都不可信**：

### 2.1 模型在输出推理过程

Ornith 默认会吐 `Thinking Process:` 再给答案。后果是双向的：

- **标签分类 0%** —— 不是模型不会分类，是输出里混着推理，取不到纯类名
- **术语纠错 100% 是假阳性** —— 我的判据是「目标词出现在输出任意位置」，
  而推理过程里自然会提到目标词

修法：`mlx-dspark serve --no-thinking`，判据改为只取**最后一行非空输出**。

### 2.2 保险杠判据撞上子串前缀

收紧后加了一道保险杠「原错词不应残留在输出中」，结果把 `这是一个ID → idea`
这个**纠对了的**案例判成失败：`norm("这是一个ID")` = `这是一个id`，
是 `norm("这是一个 idea")` = `这是一个idea` 的**前缀**，裸子串判据必然命中。

修法：残留检查加词边界 `(?![a-z])`。修完从 10/11 回到真实的 11/11。

> 教训与 M0 那次一样：**先怀疑测量方法，再怀疑被测对象。**

## 3. 标签分类：6/8，两处失败都是词表定义问题

| 输入 | 期望 | 实得 | 判断 |
|---|---|---|---|
| 我觉得可以给录音笔加个 ESP32 自动上传 | idea | idea | ✅ |
| 明天把 M2 的基准测试跑完 | task | task | ✅ |
| **今天开会讨论了接入层的传输协议** | note | **journal** | ❌ |
| 为什么 SenseVoice 的内存比 Nano 低这么多？ | question | question | ✅ |
| Ornith 那篇博客在 blog.mushroom.cv | reference | reference | ✅ |
| 今天调了一天按键事件，有点累但总算通了 | journal | journal | ✅ |
| **帮我查一下明天的日程** | command | **task** | ❌ |
| 嗯这个那个 | unknown | unknown | ✅ |

**两处失败都不该算模型的错，是我定的词表边界不清：**

1. **note vs journal** —— 「今天开会讨论了…」既是陈述性记录（note），
   又是当天的流水（journal）。ADR-0002 §3.1 里两者的定义确实重叠。
2. **command vs task** —— 「帮我查一下明天的日程」既是对助理的直接指令（command），
   也确实是一件待办（task）。

### 要改的是词表，不是模型

- **note / journal 的判据改为「是否含主观状态」**：陈述客观事实 → note；
  带情绪、体力、心境 → journal
- **command / task 的判据改为「谁来做」**：让助理立刻执行 → command；
  记下来自己以后做 → task
- prompt 里补 few-shot 示例，把这两组边界用例显式写进去

这条正好印证 jason 说的「标签是可维护、动态慢慢积累形成的」——
**边界要靠用例喂出来，不是一次性设计出来的。**

## 4. 内存：7.54 GiB 尖峰，在预算内

| 场景 | RSS |
|---|---|
| mlx-dspark 空转（模型未加载） | 0.02 GiB |
| **LLM 常驻（加载后）** | **7.17 GiB** |
| ASR 子进程单独峰值 | 0.41 GiB |
| **两者同时跑的合计尖峰** | **7.54 GiB** |

ADR-0002 估算 ~9 GiB，实测 **7.54 GiB**，✅ 在预算内且有 1.5 GiB 余量。

### 为什么比估算低：Gemma 4 的混合线性注意力

启动时带 `--kv-bits 8` 会被拒绝，报错信息给出了原因：

> `--kv-bits is unsupported for hybrid linear-attention targets
> (their recurrent-state caches are not KV caches; only 16 of 64 layers even hold KV)`

Ornith 底座是 Gemma 4，**64 层里只有 16 层持有真正的 KV cache**，其余是循环状态。
所以长上下文的 KV 内存远小于按标准 transformer 的估算——我在 ADR-0002 里
按 64K 上下文估的 ~1 GiB KV 偏高了。

## 5. 速度：36 tok/s

jason 博文实测是 M4 Pro + 8bit + dspark 投机解码约 61 tok/s。
本次是 M1 Max + 6bit + **lookup 模式**（无 drafter），36 tok/s 属于合理区间。

### 启动时踩的两个坑

1. **默认模式要求注册过的 drafter**：本地模型路径没有内置 drafter，
   必须用 `--mode lookup`（drafter-free）或 `--mode auto`。
2. **`--kv-bits` 与本模型不兼容**（见 §4）。

对 M2 的实际影响不大：术语纠错和标签分类都是短输出（几十到一百多 token），
36 tok/s 意味着单次推理 1–3 秒。

## 8. 真实长录音实测（2026-09-02，M2a 落地时补）

§1 那 11/11 是**孤立短句**上测的。M2a 接进产品链路后，拿 jason M0 录的那段
**2 分 40 秒真实语音**（`spike/audio/sample02.wav`，约 700 字）跑了一遍，
两个基准测不出来的问题露出来了。

### 8.1 长上下文里，纠错会偏向「另一个合理但错误」的术语

| ASR 输出 | jason 实际说的 | §1 孤立句里 | 本次长文里 |
|---|---|---|---|
| `ro的目录` | **raw** | ✅ `raw` | ❌ **`repo`** |

同一个模型、同一个输入片段，**放进长上下文就改错了**。而且错得很有迷惑性——
「先有一个 repo 的目录」在这段话里完全说得通，不看原音频根本发现不了。

**这意味着 §1 的 11/11 高估了真实场景的准确率。** 孤立句里模型只能从发音推断，
候选少；长上下文给了它更多「合理」的可能，反而可能压过正确答案。

**⚠️ 部分修复，且当初的「已修复」下早了（2026-09-03 更正）**：
加了项目术语表（`src/terms.rs`）之后，**短句上稳定有效**，
但**长文（700 字）上连跑 5 次 0 次通过**。T2.1.2 报「已修复」是基于
**单次通过**——那次是运气。

对照实测（同一份术语表、同一个边车）：

| 输入 | 结果 |
|---|---|
| 「然后把内容存到 ro 的目录里面」（短句） | ✅ raw |
| 「都话先有一个ro的目录，然后就存储下来」（短句） | ✅ raw |
| `sample02-asr-raw.txt`（700 字长文） | ❌ 5/5 失败，模型原样输出只调空格 |

**所以术语表解决了短句，没解决长文。** 正解是先分句再逐句纠错（T2.1.4）。

### T2.1.4 分批纠错的实测（2026-09-03）

按句子边界切成约 120 字一批之后：

| | 分批前 | 分批后 |
|---|---|---|
| 长文回归通过率 | **0/5** | **3/3** |
| 700 字纠错耗时 | 10.3 s | **~7 s** |

耗时反而降了：每批输出短，模型更稳也更快，省掉了长输出的反复。

#### ⚠️ 分批是有代价的，别只看通过率

`我的妈 book` 这一处**分批后不再被纠正**（分批前某次是纠对的）。
术语表里补了带空格的 alias（SenseVoice 会在中英之间插空格）之后仍然不纠——
**是上下文变短导致的，不是数据问题**（alias 确认已在文件里）。

所以准确的说法是：**分批把「整段全废」换成了「主体正确、个别依赖长距离
上下文的纠正会丢」**。对产品是明确的改善，但不是全赢。

⚠️ `longform_regression_ro_becomes_raw_not_repo` 原来断言「MacBook 出现」，
而文本里另一处 `macbook` 被纠对了——于是这条断言**通过了但什么都没测到**。
**已删掉该断言**：宁可少一条，也不要一条自我满足的断言。
测试判据里含子串断言时要留意这种「被别处满足」的情况。

#### codex 评审后又修掉的三个 High（2026-09-03）

分批的第一版能跑通，但有三个会在真实使用中咬人的问题：

1. **批边界的空白会被吃掉**：每批都过 `tidy()`，而它 `trim()`。
   英文在 `". "` 处切分时下一批以空格开头，trim 掉就拼成 `sentence.Next`。
   改成只把**正文**送模型，前后空白留在外面、拼接时原样恢复。
2. **`target` 只是「可以切了」不是「不许超过」**：几千字没有句号的口述
   （不停顿就会这样）仍是一整批，回到失效区间。加了 `target * 3` 的硬上限，
   并在逼近上限时优先找逗号/空格这类软切点。
   ⚠️ 原来有一条测试断言「无标点文本整段一批」——**那条测试把风险固化了**，
   已改成断言硬上限生效。
3. **部分成功被当成完整结果**：一批失败就拼原文继续，用户拿到
   「大部分纠正过、中间某段没纠」的文本，读起来完全正常而无从怀疑。
   改成**失败重试一次，仍失败则整体回退原文**——「要么全纠、要么不动」
   是可预测的，而可预测比多纠几句重要。

另加整段 45 秒总时限（5 批 × 20 秒最坏能到一两分钟，而用户正等着上屏），
以及 ASCII 句点的前视判断（`v1.2`、`blog.mushroom.cv` 里的点不是句末）。
回归测试保留并让它失败，比删掉或放宽阈值诚实——
**一个假装通过的回归测试比没有更糟**。

原文（已失效的表述）：同一份 fixture 现在稳定还原成 `raw 的目录`，且 MacBook / knowledge base /
24 小时 / Mac mini / WiFi 全部正确。回归测试
`correct::tests::longform_regression_ro_becomes_raw_not_repo` 钉住了这一条
（用转写文本当输入，不重跑 ASR——否则 ASR 的随机性会以和纠错无关的方式
让测试失败）。

⚠️ **过程比结果更值得记：提示词格式踩了五版**，其中三版单元测试全绿、
真实录音也全对，只有真去问一句「这条 road 很宽」才露馅：

| 版本 | 写法 | 实测 |
|---|---|---|
| 1 | `raw（可能被识别成：road）` | 模型**理解反了**，照括号里替换；连带把本来纠对的 MacBook / knowledge base / WiFi 全弄丢 |
| 2 | `road → raw`「遇到左边替换右边」 | 录音全对，但会误伤真实的 road（道路）、ID（编号） |
| 3 | 「仅当上下文表明…才替换」 | **仍被改**：`这条 road 很宽` → `这条 raw 很宽` |
| 4 | 加 few-shot 反例 | road 过了，`他的 ID 是 12345` → `他的 idea` |
| 5 | **去掉本身是高频普通词的 alias**（`ID`/`肉`/`日报`） | 全绿 |

第 5 版的认识：**拿正常词当「错误形式」必然误伤，而收益近乎为零**——
真实录音里 SenseVoice 本来就输出了正确的 `idea`。

另有一条测试自己的坑：判据不能写 `!contains("repo")`，因为 **`report`
里就含 `repo`**，而这段录音里恰好有「给你写个 report」。

其余纠正全部正确，包括基准里没有的几个：`我的妈 book` → `MacBook`、
`wifi` → `WiFi`、`mac mini` → `Mac mini`（大小写规范化是意外收获）、
`24R运行` → `24 小时运行`、`notice base` → `knowledge base`。

### 8.2 耗时随文本长度增长，长录音的代价远超基准

| 输入 | 纠错耗时 |
|---|---|
| §1 的短句（十几字） | 1–3 s |
| 本次长文（约 700 字） | **10.3 s** |

§5 说「单次推理 1–3 秒」，那是**短输出**的结论。纠错的输出长度约等于输入长度，
所以耗时基本随字数线性走。

**对产品的影响**：输入法场景（一句话）没问题；但录一段两三分钟的想法，
按完停止键要等十秒才上屏。菜单文案因此不能写死「慢 1–3 秒」。

**没有加长度上限**——长文本恰恰是术语更多、更需要纠错的场景，
砍掉它等于砍掉价值最大的那部分。取舍交给用户：开关默认关，文案讲清代价。

## 9. 标签分类回归（T2.2.5，2026-09-03）

`docs/agent/label-taxonomy.md` 定义的 18 条评测集，**走生产代码路径**
（`cargo test --release -- --ignored classifies_the_taxonomy`）。

### 结果：**18/18**（补 few-shot 反例后），此前是 17/18

> **2026-09-03 更新**：FU-13 在提示词里补了一条虚拟语气的反例之后，
> 唯一判错的那条也对了，连跑 3 次都是 18/18。下面保留 17/18 的记录
> 与分析——**那条判错的诊断（模型被「建任务」三字带走）正是修法的依据**。

### 此前：17/18，连跑 5 次完全一致

| | 用例数 | 命中 |
|---|---|---|
| M0 基准（提示词只有一行，无定义） | 8 | 6/8 = 75% |
| 本次（有定义 + 判别问题） | 18 | **17/18 = 94%** |

T2.2.5 的门槛是「至少 7/8」（87.5%），**达标**。

⚠️ **两组数字的用例集不同，不能直接相减。** 18 条里有一半是本轮新加的、
刻意贴着边界的用例，难度更高；但 M0 判错的那两条（note vs journal、
command vs task）现在都对。

### 唯一判错的那条，5 次全错，不是随机

```
"要是能用语音直接建任务就好了" 期望 idea 得到 task
```

「要是……就好了」是典型的虚拟语气，按定义「他承诺要做了吗？」显然没有。
模型被句中的**「建任务」三个字**带走了。

**这是模型能力问题，不是定义问题**——定义已经把判据写清楚了。所以
**不改定义去迁就它**（那会让定义为了一条用例变形）。修法是在 few-shot 里
补一条这类反例，已记进跟进账本。

### ⚠️ 一个稳定但未定位的差异

`spike/m2_bench.py` 跑同一套用例报 **18/18**（2 次一致），生产路径报
**17/18**（5 次一致）。差异稳定复现。

已排除的可能：

| 怀疑 | 验证方式 | 结论 |
|---|---|---|
| 标签顺序不同 | 受控实验，两种顺序各问 3 次 | **不是**，两种顺序都判 task |
| 期望值不一致 | 逐条比对 | **不是**，两边都是 idea |
| 规则语义不同 | 逐行 diff | **不是**，只差 markdown 星号和换行位置 |
| 解析器宽严不同 | codex 指出基准删掉所有非 `[a-z]` 字符 | 可能相关，但那条用例模型输出的是干净的 `task`，宽严都一样 |

**根因未定位。按未解决的观察记着，不替它编一个机制**
（ADR-0004 §3 有过同样的处置）。

> **2026-09-03 后续（T2.3.2）**：这个差异**从根上消除了**——
> `spike/m2_bench.py` 现在调生产二进制的 `--classify`，不再自带
> 一份提示词和解析器。两边现在报同一个分数（18/18），
> 因为它们**就是同一段代码**。
>
