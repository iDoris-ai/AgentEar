# 立项依据 — M2 收尾与 M3 摸底

记录日期：2026-09-02。本文只回答一个问题：**接下来这三件事，凭什么值得做。**
每条都必须指向仓库里已有的实测数据，不接受「感觉需要」。

---

## 1. 项目术语表：由一次真实失败逼出来的

M2a（技术术语纠错）已经合并（PR #9）。它解决的是 M0 发现的硬问题：`raw` 一词
四个 ASR 模型全错（row / road / ro / roll），`Docker` 变成 `doocca`。
ADR-0001 判定换 ASR 模型解决不了，只能靠下游 LLM 结合上下文纠正。

M2a 的基准是 11/11 全对。但接进产品链路、拿 jason 本人 2 分 40 秒的真实录音跑完，
出现了一个基准测不出来的失败（详见 `docs/benchmarks-m2.md` §8.1）：

| ASR 输出 | 实际说的 | 孤立句测试 | 700 字长文里 |
|---|---|---|---|
| `ro的目录` | raw | 纠对了 | **纠成了 `repo`** |

同一个模型、同一个片段，放进长上下文就改错。而且「先有一个 repo 的目录」在那段话里
完全说得通，不对着原音频根本发现不了。

**结论：孤立句基准高估了真实准确率。** 长上下文给模型更多「合理」候选，
反而压过正确答案。让模型每次从上下文猜是错的路子——它需要的是一份
**本项目固定词汇的清单**。ADR-0002 提过术语表但一直没做，现在有了必须做的证据。

## 2. 标签识别与路由：卡在定义，不是卡在模型

README 定的产品链路里，转写之后要按语音内容里的标签分流到不同分支
（用户说「这是一个 idea」「这是一个任务」，系统据此选下游）。
M0 的 M2 基准把这条也测了，结果是 **6/8**：

| 判错的两条 | 期望 | 模型给的 |
|---|---|---|
| 今天开会讨论了接入层的传输协议 | note | journal |
| 帮我查一下明天的日程 | command | task |

**两处失败都不是模型能力问题，是词表定义问题。** 「开会讨论了什么」既像随手记
（note）也像当天流水（journal）；「帮我查日程」既是给系统的指令（command）
也是一件待办（task）。人看了都会犹豫的边界，不能指望模型稳定。

所以这个 Feature 的第一步不是写代码，是**重新定义那 8 个类的边界并给出判别依据**，
再用 few-shot 把边界示范给模型。定义不清就开工，等于把 6/8 固化下来。

## 3. TTS 方言可行性：M3 最大的未知，可能推翻整个设计

jason 2026-09-02 补充了一条以前不在任何文档里的约束：**输出语音要能说
台湾话、广东话、香港话、英语、泰语**（可先做普通话或英语）。

这不是锦上添花。多数中文 TTS 只做普通话，闽南语和粤语的可用方案少得多。
如果本地根本没有可用的闽南语 TTS，M3「语音输出与打断」的设计就得改——
要么接受只做普通话，要么引入云端（**与隐私约束正面冲突**），要么推迟 M3。

`docs/milestones.md` 的 M3 一直写着「TTS 尚未选型」，而选型的第一个问题
不是「哪个更好」，是「到底有没有」。这一步只回答有没有。

⚠️ **注意方向不要混**：这里说的是**输出侧**（让它说方言）。输入侧（听懂方言）
是另一件事——现有 SenseVoice 覆盖 zh/en/yue/ja/ko，**粤语能听、闽南语听不了**，
那个缺口记在 `docs/milestones.md`，需要 jason 单独拍板才能动。
