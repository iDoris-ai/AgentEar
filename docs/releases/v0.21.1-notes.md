## v0.21.1 —— 修「双击进对话模式后，第一轮没有回答」

jason 2026-09-26 装上 v0.21.0 实测：提示音单击、双击都正常，
**但双击进对话模式说了一句，没有回答**。查日志是两个 bug 叠在一起。

### Bug 1：端口被别的程序占着，被当成「语音服务没起」

TTS 服务默认在 `127.0.0.1:8765`。这台机器上这个端口被另一个 app
（Chat On Steroids）占着，对 `/health` 回 **HTTP 401**。

旧逻辑只分「活 / 没活」，401 算「没活」→ 去拉起 TTS 服务 →
服务发现端口被占，立刻退出 → 日志里只有「启动后立刻退出」「90s 内没就绪」，
**真正的原因（端口被别人占了）一个字都没有**。

现在分三种：

| 探到的情况 | 判成 | 会不会去拉起 |
|---|---|---|
| `/health` 回 2xx | 在跑 | 不用拉 |
| 连接被拒（没人在听） | 没起 | 按配置拉起 |
| 有程序在听但不对（401 / 404 / 500 / 超时…） | **端口被占** | **不拉**，并说清是谁占的、该改哪里 |

日志和 `agentear --diagnose` 现在会这样报：

```
❌ TTS 边车的地址 http://127.0.0.1:8765 被别的程序占了（有程序在听，但 /health 回了 HTTP 401，
   占着它的是 Chat On Steroids（pid 59906））——不会去拉起。改 config.json 的 tts_url，
   并在 talk_tts_start_command 里加 AGENTEAR_TTS_PORT=<新端口>；或者关掉占着端口的那个程序
```

### Bug 2：切进对话模式的第一轮，和语音服务的启动赛跑

双击那一刻才在后台启动 LLM / TTS 两个服务，而你说完一句（约 3 秒）就去请求 TTS——
那时 TTS 还在加载，**第一轮必然失败**，即使端口没被占。

现在：服务正在启动时，这一轮的回答**先等它启动完**，最多等 30 秒
（本机实测两个服务串行约 13 秒，30 秒留了两倍多余量）。
等待在回答线程里进行，**不影响按键**：等的期间你又按键开始说下一句，
这一轮迟到的回答就作废，不会在你说话时突然开播。
另外，服务正在启动时再双击，不会再重复启动第二份。

### 验证

- `cargo test`：321 passed / 0 failed / 7 ignored（新增 11 条：探活真值表、
  用真 curl 打一个回 401 的端口、关闭的端口、端口解析、`lsof` 输出解析、
  等待闸的四种时序、迟到回答作废的判据）。
  两处变异（把 401 判回「没起」、让等待直接返回）都会让新测试变红。
- 本机冒烟（用这个版本的二进制）：
  - `--diagnose` 对默认端口 8765 报出「被 Chat On Steroids（pid 59906）占了」；
    对改到 8766 的真实配置报两个服务都在跑。
  - `--say` 出声。
  - 把当时**没回答的那一段录音**用 `--talk-turn` 重放：完整一轮出声。

### ⚠️ 没测到的（需要你手测）

- **守护进程里的真实链路**：「双击 → 说一句 → 等服务启动 → 出声」这一条
  没有用真按键测过（后台环境没有麦克风权限）。请在对话模式没开、两个服务都没跑的状态下
  双击说一句，确认第一轮就有回答（可能要多等十来秒）。
- 如果你的 TTS 仍在默认端口且被占着，这个版本**不会**自动换端口，只会把原因说清楚——
  要改 `config.json`（你本机已经改到 8766）。
