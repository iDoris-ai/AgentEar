## v0.19.0 —— 修复播放期间按录音键实际打不断的真 bug + 泰语 code-switch 提示词

两件事：一个是本轮复查揪出的真功能 bug（V1 打断此前在守护进程里从未真正生效），
一个是给 whisper 泰语引擎加了术语提示词。

### 1. 修复：播放期间按录音键在守护进程里此前完全打不断

**这是本版最重要的修复**，也是这个版本存在的主要理由。

对话模式下，`worker()` 主循环是唯一读录音键事件（`rx.try_recv()`）的地方，而
播放回答的 `answer_out_loud(...)`（LLM → TTS → `play_blocking()`）此前是**同步
调用**，会一路阻塞到这一轮播完才返回。于是播放期间用户按键，事件确实被送进了
channel，但 worker 线程没有机会回到循环顶部去读它——只有播完之后才会处理，
`talk::stop_playback()` 因此从未在真实播放中被触发过。**这个 bug 存在于所有
带通话链路的历史版本（v0.6.0 起），不是这一版才引入的**，只是这一版才发现并修掉。

修法：把 `finish()` 里那次 `answer_out_loud(...)` 调用改成 `std::thread::spawn`
起一个线程去跑。worker 循环立刻能回到 `rx.try_recv()`，用户按键时会先
`stop_playback()` 掐掉正在播的声音，再开新一段录音。

⚠️ **验证边界**：过了 `cargo build` + 全量 `cargo test`（294 passed）+ 代码走读
确认根因与修法对应。**没有在真实守护进程上用物理键盘实测过**——建议升级后手动
验收一遍：对话模式下让它念一句长回答，播放中按一下录音键，确认声音立刻停、
新一段录音立刻开始。

**记进 backlog、这一版没有一起修的两条同类遗留**（T3.4.15）：
- 命令二次确认的"念问句"（`announce_pending`）是同一类同步阻塞，播放期间同样打不断。
- 进程退出（菜单 Quit / 信号）时，如果恰好有播放在进行，`afplay` 子进程可能不会
  被清理干净（`Player` 是 `static`，进程退出时 Rust 不跑它的 `Drop`）。

### 2. 泰语 code-switch：给 whisper 加 initial prompt

复用 Qwen3-ASR 已经在用的"取术语表里的拉丁词、40 词封顶"逻辑（`latin_context_
from_terms`），作为 whisper 泰语引擎的 `--prompt` 参数。之前只有 Qwen3-ASR 后端
吃得到这份术语表，whisper 后端（默认泰语引擎）完全没有，中英夹杂场景下更容易把
Docker / Kubernetes 这类术语识别错。

**per-call 现算，不缓存**：每次转写都重新从 `terms.json` 读一遍，用户改完术语表
下次录音即生效——这是延续 M2 已经定的规矩，不是这次新加的例外。
