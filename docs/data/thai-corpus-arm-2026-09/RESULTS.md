# 泰语 code-switch 评测结果（2026-09-03）

**被测**：`distill-whisper-th-large-v3` q5_0（**当前发布版用的就是这个**），
经 `vendor/bin/whisper-cli`。
**语料**：本目录 22 条（16 条夹英文 + 6 条纯泰语对照组）。

---

## 结论

1. **模型的泰语很好**（对照组 CER 3.9%，6 条里 3 条逐字全对）。
2. **问题 100% 是「把拉丁字母音译成泰文」**——39 个英文词有 36 个被写成泰文。
   **声学上模型听懂了**（`ดอกเกอร์` 念出来就是 Docker），是书写形式不对。
3. **最有效的修法是给 whisper 一个短的 initial prompt** ——
   用**我们已经在发的那份术语表**（`terms.json`）当 prompt，
   夹英文 CER **31.1% → 18.4%**，英文词命中 **8% → 51%**，
   而且纯泰语还略有改善（3.9% → 3.1%）。**改动约 10 行，不需要边车，不需要换模型。**
4. ⚠️ **但 prompt 太长会把模型彻底搞坏** —— 100 词的通用词表让纯泰语
   CER 从 3.9% 崩到 **53.7%**。这是个必须设护栏的参数。

---

## 一、基线：问题有多大

| 组 | 条数 | CER 均值 | CER 中位 | 英文词命中 |
|---|---|---|---|---|
| **`control_thai_only`（对照组）** | 6 | **3.9%** | 2.6% | —（本来没有英文） |
| `daily_collaboration` | 8 | **31.0%** | 34.9% | **0 / 16（0%）** |
| `devops` | 8 | **31.3%** | 32.5% | **3 / 23（13%）** |

**纯泰语 3.9% vs 夹英文 31.1% —— 8 倍。**
每条连跑 3 遍，**22 条输出全部一致，0 条不确定**：这些数字不是采样噪声。

> 样本量小（n=22）削弱的是「不同模型之间的小差异」，
> 削弱不了「同一模型内部 8 倍的组间差异」。

**对照组是这批语料最值钱的部分。** 没有它，31% 说明不了是「泰语差」还是
「一夹英文就崩」，也就没法据此决定改哪里。

### 失败模式

| 保住拉丁字母（3） | `deploy` `production` `server` |
|---|---|
| **被音译成泰文（36）** | `review` `code` `bug` `fix` `push` `branch` `develop` `comment` `GitHub` `performance` `API` `optimize` `query` `design` `document` `Notion` `Docker` `container` `Kubernetes` `cluster` `merge` `pull` `request` `unit` `test` `build` `CI` `Slack` `PostgreSQL` `cache` `Redis` `zone` `memory` `leak` `service` `version` |

```
参考: เราใช้ Docker สร้าง container แล้วส่งขึ้น Kubernetes cluster
输出: เราใช้ ดอกเกอร์ สร้างคอนเทนเนอร์ แล้วส่งขึ้น กูเบอร์เนสต์ ตีด คัตเตอร์
      ↑Docker      ↑container          ↑Kubernetes    ↑cluster
```

## 二、五个配置横比

| 配置 | 纯泰语 CER | 夹英文 CER | 英文词命中 | 评价 |
|---|---|---|---|---|
| **A 当前发布** `-bs 1 -bo 1` | 3.9% | 31.1% | 3/39（8%） | 基线 |
| **B 默认 beam search** | 3.9% | 30.8% | 5/39（13%） | **几乎没用** |
| **C 默认 + 语料词表 prompt** | 3.1% | **10.8%** | **26/39（67%）** | ⚠️ **有泄漏**，见下 |
| **D 默认 + 现有 `terms.json`** | **3.1%** | **18.4%** | **20/39（51%）** | ✅ **可直接落地** |
| **E 默认 + 100 词通用词表** | **53.7%** 💥 | **82.3%** 💥 | 2/39（5%） | ❌ **把模型搞坏了** |

### B：解码参数不是根因

`src/asr.rs` 传的是 `-bs 1 -bo 1`（贪心解码）。**换成默认 beam search 只换来
2 个词、CER 改善 0.3 个百分点。** 一开始怀疑它是根因，实测否掉了。

### C 的 67% 不能当成可交付的数字

那个 prompt 是**照着测试语料的词表写的**。生产里用户不会预先告诉我们他要说什么。
它的价值只在于**证明机制有效**、给出上界。

### D 是诚实的数字，而且意外地好

`terms.json` 是**语料到手之前就在仓库里**的，它含的 54 个拉丁词里
**只有 `docker` 和 `kubernetes` 出现在这批语料中**（2/39 覆盖率）。

**但它救回了 20 个词。**

说明 initial prompt 起的不是「查表替换」，而是**「保持拉丁书写」的语域提示**——
一串拉丁技术词让解码器整体倾向于不做音译，**包括表里没有的词**。

这条很要紧：它意味着**不需要枚举用户的全部词汇**就能拿到大部分收益。

### E：太长的 prompt 是灾难，不是「效果差一点」

100 词的通用词表让**对照组**（纯泰语，本来 3.9%）崩到 **53.7%**。
失败模式是 whisper 的典型退化：

```
截断      参考: เมื่อเช้าฝนตกหนักมาก ทำให้รถติดกว่าปกติ
          输出: เช็ดตรวง

语言漂移   参考: ผมออกจากบ้านตั้งแต่หกโมงครึ่ง แต่ยังไปถึงที่ทำงานสาย
          输出: ผม I have to be moved to the most

重复循环   输出: ผมจะคอมเม็นรายละเอียดไว้ในกิจหับให้ได้ไว้ในกิจหับให้ดู
          输出: ...ตอนนี้ API API ตอบกลับกลับกลับชาร์กว่า 2 วินาที
```

`whisper-cli --help` 写明 initial prompt 上限是 `n_text_ctx/2` tokens。
**落地时必须有长度护栏**，而且护栏值要实测——C（约 37 词）好、D（54 词）好、
E（约 100 词）崩，**拐点在哪没测**。

## 三、M2 术语纠错这条路：试过了，不够

最初以为该由 M2 的 LLM 术语纠错来修（它在中文上解决同类问题）。**实测不成立**：

| 做法 | 夹英文 CER | 英文词命中 |
|---|---|---|
| 不纠错 | 31.1% | 3/39 |
| **现有纠错（术语表驱动）** | 28.5% | **5/39** |
| 换成「音译还原」专用提示词 | 26.0% | 11/39 |

- **现有纠错只认术语表里的词**：22 条里 **20 条完全没动**。
- 唯一生效的那条（`devops/arm-002`）**捆绑了一个稳定幻觉**：
  `cluster` → `กด Ctrl+C`（「按 Ctrl+C」），**3 遍一模一样**，不是采样噪声。
  这正是 ADR-0002 §4.3 说的「纠错是有损操作」——代价是真的。
- 就算换专用提示词也只到 11/39，**还要挂着 7.8 GB 的边车**，
  而 D 方案 0 依赖就到 20/39。

**结论：这个问题该在解码时解决，不该在事后解决。**

## 四、还没验证的

1. **「换泰语模型也一样」仍是推断。** 要证实，得把 ADR-0004 的另两个候选
   （Thonburian medium / typhoon-whisper-turbo）在这批语料上跑一遍。
   **那两个模型文件已经不在机器上了**，要重跑 `scripts/build-thai-model.sh`。
   在那之前这只是一个有依据的猜测。
2. **prompt 长度的拐点没测。** C/D 好、E 崩，中间没有数据点。
3. **C/D/E 每条只跑了 1 遍。** 依据是 A 在这一轮的数字（31.1% / 3-39）
   与前一轮 3 遍重复的结果**逐位一致**，说明 whisper 在这套参数下是确定性的。
   但落地前 D 应该按 3 遍复核。
4. **单一说话人。** 结论的措辞只能是「Arm 这个说话人」。

## 五、`impromptu` 那 184 秒：用来测长音频（已跑）

没有参考文本，**算不了 CER**。但 ADR-0004 §3 明说 whisper 路径的内存增长
「98 秒之外是未验证」，这条文件把验证范围从 98 秒推到 **184 秒**：

| | 实测 |
|---|---|
| 音频时长 | 184.1s |
| 转写耗时 | 21.6s |
| **RTF** | **0.117** |
| **峰值 RSS** | **820 MB** |
| 输出 | 1536 字符，内容连贯（自我介绍，无重复循环） |

820 MB 在 M2 阶段的 9 GiB 预算内宽裕。**但这仍然只到 3 分钟**——
ADR-0004 §3 要的是 5/15/30/60 分钟，那几档依然未验证，
**不要拿这个数字当那一项的结论**。

## 六、CER 的口径

**去掉所有空白后做字符级编辑距离，拉丁字母转小写，不做任何泰语正规化。**

去空白的理由：泰语词间不加空格，参考文本里的空格是短语停顿，ASR 不会稳定复现，
留着会把「没打空格」算成错误。

**口径一变，历史数字就不可比。** 要改口径就得把上面全部重跑。
