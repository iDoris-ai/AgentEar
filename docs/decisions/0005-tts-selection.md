## 1. 背景与约束

`docs/milestones.md` 的 M3 要「语音输出与打断」。jason 2026-09-02 补了一条
以前不在任何文档里的约束：

> **输出语音要能说方言**：台湾话、广东话、香港话、英语、泰语。
> 允许分阶段——先做普通话或先做英语都行。

加上全局的隐私红线：**任何需要把文本或音频送第三方服务器的方案直接出局**。

⚠️ **方向不要混**：这里说的是**输出侧**（让它说方言）。输入侧（听懂方言）
是另一件事——现有 SenseVoice 覆盖 zh/en/yue/ja/ko，**粤语能听、闽南语听不了**，
那个缺口记在 `docs/milestones.md`，需要单独拍板。

## 3. 决策要卡在哪一步，取决于 Q3 的答案

### 情形 A：`nan_tw_000.wav` 确实是闽南语

那么 **OmniVoice 是最有希望的单一候选**：一个模型覆盖多语言、已在目标机器上
跑通、速度和内存都可接受。

接下来要做的（不在本文范围）：
1. **查清许可** —— `mlx-community/OmniVoice-bf16` 没有模型卡也没有许可标注，
   而我们要随包分发或按需下载。上游是谁、什么许可，必须查到白纸黑字。
   （泰语模型那次的经验：MIT 最省事，Apache-2.0 要看 NOTICE，
   自定义许可要逐条读。）
2. **测方言质量** —— 「能说」和「说得像」是两件事，要母语者判断。
3. **测语言/音色的控制方式** —— CLI 看着不支持，可能要走 Python API。

### 情形 B：`nan_tw_000.wav` 是普通话念汉字

那么 OmniVoice 的「646+ 语言」不包含闽南语，**要么换模型，要么放弃方言**。

下一步是验证 `MERaLiON-OmniVoice-Hokkien` 与 `mlx-community/OmniVoice-bf16`
**是否同源**（两者都叫 OmniVoice、都有 `audio_tokenizer` 子目录，架构上很可能
是同一个基座）。若同源，那份闽南语微调权重理论上可以转成 MLX 格式再用
mlx-audio 跑——**和泰语 whisper 那次是同一套路数**（转换 + 量化 + 校验指纹）。

⚠️ 但那是**新加坡闽南语**，不是台湾话。台湾话对口的是 BreezyVoice-Taigi，
而它能不能在 Apple Silicon 上跑完全没测。

## 4. 如果闽南语最终没有可用方案，M3 的三条走向

**这一节是给 jason 拍板用的，本文不替他选。** 每条都列了代价。

### 走向一：只做普通话 + 英语，方言推迟

- **代价**：方言这条约束落空。但 jason 自己说过「先完成普通话或先完成英语的都可以」，
  所以这不违背他的意图，只是把方言从 M3 挪到更后面。
- **好处**：M3 立刻可做。Qwen3-TTS（Apache-2.0、许可最干净、已在 mlx-audio 上）
  就够用，连许可都不用纠结。
- **风险**：如果方言是真需求，推迟等于一直不做——因为没有触发它的时间点。

### 走向二：推迟整个 M3，先做 M2b / M3.5

- **代价**：agent 的「嘴」一直没有。而 jason 明确说过 AgentEar 是
  「agent 的耳朵和嘴巴」，只有耳朵是半个产品。
- **好处**：M3.5（录音笔刻画）本来就是「到手即做、不排队」，
  而那台机器还没到手；M2b（知识库投递）也还没做。不缺活干。
- **风险**：TTS 的未知不会因为推迟而变少。

### 走向三：接受「TTS 只做普通话，但方言用别的路子」

比如：方言内容仍然输出**文字**，只有普通话/英语走语音。

- **代价**：体验不一致，用户要记住「哪些语言会读出来」。
- **好处**：不阻塞 M3 主体（AEC、打断式半双工才是 M3 真正的工程量），
  方言可以在 TTS 侧有方案时再补上。
- **风险**：这是个折中，做完可能两边不讨好。

   （`docs/asr-selection.md` §4 已经把阈值列好了）。选型卡住不代表 M3 卡住，
   AEC 那块随时可以开始。
