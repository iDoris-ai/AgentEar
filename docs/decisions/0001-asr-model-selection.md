# ADR-0001：本地 ASR 模型选型

- **状态**：已接受（2026-07-29）
- **决策**：主链路使用 **SenseVoiceSmall q8 + FSMN-VAD**，通过 `llama-funasr-sensevoice` 单二进制调用
- **推翻**：本文档取代 `docs/asr-selection.md` 中「Fun-ASR-Nano 为主链路」的暂定结论
- **实测依据**：`docs/benchmarks.md`

---

## 1. 背景

AgentEar 需要一个**全本地**的中文语音转文字引擎，约束来自 README 定的两条不可让步的原则（隐私、成本）以及 jason 定的资源上限：

| 约束 | 值 |
|---|---|
| 常驻内存 | ≤ 2 GiB |
| 语种 | 中文为主，含方言口音；中英混杂技术术语频繁 |
| 实时性 | 需要流式 / 低延迟 |
| 运行时 | **不得为常驻守护进程引入 Python 运行时** |
| 机器 | MacBook Pro M1 Max，64 GB |

初版选型（`asr-selection.md`）基于**二手资料**选了 Fun-ASR-Nano，标记为「暂定」。本 ADR 记录实测横比后的最终决策。

---

## 2. 实测数据

同一段语料（jason 口述 README 的语音备忘录，119.64s）、同一台 M1 Max、同一个 FSMN-VAD。

| 模型 | 权重 | RSS(2min) | RSS(30min) | 破 2GiB 时长 | RTF | CER | 术语 | 标点 | 运行时 |
|---|---|---|---|---|---|---|---|---|---|
| Fun-ASR-Nano q4km | 910 MiB | 1.53 GiB | **2.45 GiB ❌** | **16 分钟** | 0.062 | **24.75%** | 9/13 | ✅ | 单二进制 |
| **SenseVoiceSmall q8** | **242 MiB** | **419 MB** | **1.27 GiB** | 54 分钟 | 0.033 | 25.08% | **10/13** | ✅ | **单二进制** |
| Paraformer q8 | 226 MiB | 315 MB | 1.25 GiB | 52 分钟 | 0.036 | 25.75% | 8/13 | **❌ 无标点** | 单二进制 |
| Qwen3-ASR-0.6B 8bit | 960 MiB | 1.18 GiB | 1.57 GiB | **61 分钟** | 0.029 | 24.92% | **10/13** | ✅ | **❌ Python+MLX** |

### 2.1 准确率无法区分

**CER 四家落在 24.75–25.75%，相差不到 1 个百分点。**

必须说明这个数字的性质：参考文本是 jason 口述 README 的**另一个 ASR 转写结果**，不是人工逐字稿（它自身有 `mark book`→MacBook、`row`→raw、`二四小时`→24小时 等错误）。所以这测的是「系统间分歧率」，真实 CER 应低于此。

**结论：单样本上四个模型的准确率无法区分，选型必须靠其他维度。**

### 2.2 关键术语命中（人工逐项判定）

| 正确词 | 参考 | Nano | SenseVoice | Paraformer | Qwen3-ASR |
|---|---|---|---|---|---|
| MacBook | ✓ | ✓ | ✓ | ✓ | ✓ |
| Mac mini | ✗ | ✗ | **✓** | ✗ | **✓** |
| **raw 目录** | ✗ | ✗ | ✗ | ✗ | ✗ |
| knowledge base | ✓ | ✗ | ✗ | ✗ | **✓** |
| 24小时 | ✗ | ✗ | **✓** | ✗ | **✓** |
| 本地模型 | ✓ | ✓ | ✗ | ✗ | ✓ |
| idea | ✓ | ✓ | ✓ | ✓ | **✗**（→ID） |
| report | ✓ | ✓ | ✓ | ✓ | **✗**（→日报） |
| AI / wifi / 爱国者 / 闲鱼 / 8G | ✓ | ✓ | ✓ | ✓ | ✓ |
| **命中** | 10/13 | **9/13** | **10/13** | 8/13 | **10/13** |

**`raw` 四家全错**（row / road / ro / roll）。这是一个跨模型的确证：**没有任何 ASR 能靠自身解决中英混杂技术术语**，只能靠下游 LLM 结合上下文纠正。

### 2.3 内存增长曲线

四个模型的 RSS 都随音频长度线性增长，差别在**基线**和**斜率**：

| 模型 | 增长率 | 破 2 GiB 的音频长度 |
|---|---|---|
| Fun-ASR-Nano | 0.56 MB/s | **16 分钟** |
| Paraformer | 0.58 MB/s | 52 分钟 |
| SenseVoiceSmall | 0.52 MB/s | 54 分钟 |
| Qwen3-ASR | **0.24 MB/s** | **61 分钟** |

**原选型 Fun-ASR-Nano 恰好是四家里唯一在 30 分钟就爆预算的。**

### 2.4 启动开销（决定 M1 架构）

| 模型 | 冷启动（含加载） | 热运行 |
|---|---|---|
| Fun-ASR-Nano | **11.45s** | 1.0s |
| SenseVoiceSmall | **0.17–0.21s** | 同左 |

Nano 载入 910 MiB 权重需 10.5 秒；SenseVoice 只有 242 MiB，加载几乎无感。

## 3. 决策

### 采用 SenseVoiceSmall q8

**理由不是准确率（四家等同），而是工程形态：**

1. **常驻 419 MB，是 Nano 的 27%** —— 省下的 1.1 GiB 留给 M2 的本地 LLM
2. **长音频撑到 54 分钟，Nano 只到 16 分钟** —— 差 3.4 倍
3. **冷启动 0.2 秒 vs 11.45 秒** —— 直接消除了 M1 的冷启动问题（见 §5）
4. **单二进制零 Python** —— 符合硬约束
5. **术语命中 10/13 反超 Nano 的 9/13**

### 落选理由

| 模型 | 出局原因 |
|---|---|
| **Fun-ASR-Nano** | 内存基线过高，16 分钟即破预算；冷启动 11.45s |
| **Paraformer** | **完全不输出标点**。内存最小、CER 只差 1 个百分点，但对一个把语音变笔记/任务的产品是硬伤 |
| **Qwen3-ASR-0.6B** | 需要 **Python + MLX 运行时**，违反硬约束。Rust 守护进程要用它只能 shell out 给 Python，等于把 Python 塞回常驻链路 |

**Qwen3-ASR 是可惜的一个**：内存增长率只有其他三家的一半，术语最强（唯一答对 `knowledge base`）。**如果将来出现 GGUF 或纯 Rust 推理路径，应重新评估。**

### 更正一处早先的错误

`asr-selection.md` §1 称 SenseVoice「官方标注即将停止维护」，来源是厂商博客（funasr.com）的二手说法。**核实后不成立：**

- GitHub `QwenAudio/SenseVoice`：未 archive，最后提交 2026-07-27，8951 stars
- HF `SenseVoiceSmall-GGUF`：下载量 5755，**高于** Fun-ASR-Nano-GGUF 的 4813

这曾是排除 SenseVoice 的主要理由，它站不住。

## 4. 全模态模型：评估后不采用（改为按需分层）

jason 提出把内存预算放宽到 3–4 GiB，换取语音 + 图片 OCR 的全模态能力。

### 实际体积

| 模型 | 权重合计 | 3–4 GiB 预算 |
|---|---|---|
| **Qwen2.5-Omni-3B** | **3.4 GiB**（主体 Q4_K_M 2007 MiB + mmproj Q8 1467 MiB） | ⚠️ 卡在边缘 |
| MiniCPM-o 4.5 | **6.1 GiB**（Q4_K_S 4579 + audio 630 + vision 1044） | ❌ 超一倍 |
| Qwen3-Omni-30B-A3B | 4bit 约 15 GiB | ❌ |
| Nemotron-3-Nano-Omni-30B | 4bit 约 15 GiB | ❌ |

MiniCPM-o 的 6.1 GiB 与 jason 博客 `minicpmo-omni-model-developer-guide-selection.md` 中「Int4 约需 8–12GB 内存」吻合。

### 决策：不替代 ASR，改为按需分层

```
常驻层（始终在内存）
  SenseVoiceSmall q8   242 MiB   ← 只做语音转文字

按需层（用时加载，用完卸载）
  ├─ 本地 LLM              ← M2：标签路由 + 术语纠错
  └─ 全模态模型  3.4 GiB    ← 截图 OCR、看图提问
```

**三条理由：**

1. **常驻与按需是两种东西。** ASR 必须永远在线（要一直听），图片 OCR 是偶发的。分层后常驻开销是全模态方案的 **7%**，能力完全一样。为偶尔用的功能付永久内存租金不划算。
2. **全模态模型不是为连续转写设计的。** 它吃「一段音频 + 一个问题」，而路径 A 是小时级连续转写。§2.3 已证明 RSS 随音频长度增长，3B 模型只会更陡。
3. **速度差一个数量级。** SenseVoice 是 30 倍实时 / 419 MB；3B 全模态在 M1 Max 上转写乐观估计 2–5 倍实时，对「按键即出字」的体验差别明显。

**全模态属于 M2 之后的按需层，不占 ASR 的位置。**

---

## 5. 本决策对后续里程碑的影响

### M1 架构大幅简化

SenseVoice 冷启动 0.2 秒意味着：

- **不需要常驻模型服务**，每次录音直接 `Command::new()` 调子进程即可
- **不需要链接 C++ 库**，用官方预编译二进制
- **冷启动问题消失**，`milestones.md` 里为 Nano 的 10.5s 加载写的「开机加载 <15s 且状态可见」不再必要

### 仍然有效的约束

1. **长音频必须分段送入**，单段建议 ≤5 分钟（SenseVoice 的窗口比 Nano 宽松得多，但增长率仍是 0.52 MB/s）
2. **特殊 token 需过滤** —— `llama-funasr-sensevoice` 有 `--keep-tags` 开关，默认行为需在 M1 中验证
3. **术语纠错是 M2 的职责** —— §2.2 的 `raw` 全军覆没坐实了这一点

---

## 6. 需要复核本决策的条件

- Qwen3-ASR 出现 GGUF 或纯 Rust 推理路径（它的指标最好，只输在运行时）
- M1 实测中 SenseVoice 的中文准确率不可接受（本决策基于**单个样本**，样本量不足）
- 出现 ≤1 GiB 的全模态模型

## 7. 遗留未测

- **FireRedASR2-AED**：需单独的 CrispASR 运行时，q4_k 权重 918 MiB。作为「离线高精度兜底组」的候选另行评估，不影响主链路。
- **Qwen2.5-Omni-3B 实测**：仅查证了权重体积，未实测 RSS/速度。属于按需层，不阻塞 M1。
- **嘈杂环境语料**：现有样本均为安静环境（-30.8 / -32.7 dB）。
- **热行为/降频**：30 分钟跑完未见性能衰减，但未做温度采样。
