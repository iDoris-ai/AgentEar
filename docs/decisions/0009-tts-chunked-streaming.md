# ADR-0009：TTS 首包延迟——参考音色缓存 + 分块流式（提案，Phase 0/1 已完成）

- 状态：**调研中**（jason 2026-09-19 发起；Phase 0 已用真实数据核实；
  **方案 A 的 Phase 1 spike 已跑通，总耗时降到约 1/3**，见 §5.1；Phase 2 待排期）
- 影响：不改 `/speak` 现有契约（新增端点，老端点不动）；涉及 fork/包一层
  `mlx_audio` 的 `VoxCPM2.Model` 内部实现，不是官方公开 API
- 相关：ADR-0007（实时语音架构，`/speak` 契约定死在这里）、
  `docs/benchmarks-talk.md`（TTS 时延实测的权威数据源）、
  `docs/agent/tasks.md` T3.4.8（句子级流水线，同一类"重叠等待"优化，这次是它的下一层）

---

## 0. 一句话

**对话模式里"说完话到听到回答"要等 7–12 秒，64GB 内存帮不上忙——这是算力瓶颈，
不是内存瓶颈。** 排查发现两个独立的优化点，**第一个比原计划的"分块流式"更便宜、
收益可能更大**：① VoxCPM2 每次合成都要把参考音色的 465 字参考文本重新过一遍模型
（固定成本，跟要说的话无关，占了短句一半以上的耗时）；② 官方 VoxCPM2 本来就是
逐 160ms patch 自回归生成的，我们用的 `mlx_audio` 移植版只是没把这个"边生成边吐"
的能力接到对外接口上。

## 1. 背景：为什么要查这个

jason 用对话模式实测「说完话到听到回答」要 7 秒以上，问「64GB 内存都还慢，
为什么？」。排查过程（详见会话记录，不重复贴）：

1. 先排除了内存容量——模型只有 2.3–3.3 GB，64 GB 用不上，瓶颈是 GPU/Metal 算力。
2. 发现在跑的是 8bit 而不是文档默认的 4bit（`config.json` 手动配过），切回 4bit
   后从 7–9s 降到 4.9s（一次干净测量），但重复测试后发现方差很大（4.9s–12s 都出现过），
   系统负载（load average）与之无明显相关。
3. 顺着这条查到 **VoxCPM2 是"diffusion-autoregressive"混合架构**，官方仓库
   （[OpenBMB/VoxCPM](https://github.com/OpenBMB/VoxCPM)）原生支持流式
   （`model.generate_streaming()`），但**我们用的 `mlx_audio`（MLX/Apple Silicon
   社区移植版）没有实现这个方法**——只有整句合成完才一次性返回的 `generate()`。

这份 ADR 记录第二轮更深的排查（Phase 0）：不满足于"知道流式没接上"，
而是**真实测量了合成流程内部每一步的耗时**，结果发现了一个比"接上流式"
更便宜的第一步。

## 2. 架构事实：VoxCPM2 在 `mlx_audio` 里到底是怎么生成的

翻源码（`mlx_audio/tts/models/voxcpm2/voxcpm2.py`）确认：**生成过程本来就是
逐 patch 自回归的**，不是"一次性对整句做扩散"：

```python
for i in range(max_tokens + warmup_patches):        # 外层循环：一个 patch 一个 patch 生成
    pred_feat = self.feat_decoder.sample(
        mu=dit_h, n_timesteps=inference_timesteps,    # 只对"这一个 patch"跑 10 步扩散
        patch_size=self.patch_size, cond=cond_in,
    )
    pred_feat_seq.append(pred_feat[...])
    ...
    new_lm_out, lm_cache = self.base_lm(inputs_embeds=curr_embed, cache=lm_cache)  # 自回归喂回去
    if real_steps > min_tokens and stop_flag == 1:
        break

# 循环全部跑完才做这一步：
all_feats = mx.concatenate(pred_feat_seq, axis=1)
audio = self.audio_vae.decode(all_feats_flat)          # 唯一的"一次性"操作
yield GenerationResult(...)                              # 只 yield 一次
```

算出 `patch_size=4`、`decode_chunk_size=1920`（`decoder_rates=[8,6,5,2,2,2]` 连乘），
**每个 patch = 7680 采样点 / 48000Hz = 160ms 音频**。也就是说模型内部本来就是
"每 160ms 生成一段、自回归喂给下一段"，卡住流式的只是**最后这一步"全部生成完
才一次性 decode + yield"**。代码里甚至已经有 `streaming_prefix_len` 参数和一段
"带上文 patch 解码、再裁掉上文"的逻辑（`has_continuation` 分支）——这正是
分块流式解码需要的技巧，模型/配置层面看着像本来就是照流式设计的。

## 3. Phase 0：真实测量，不是估算

用一个独立脚本（不碰生产代码）加载同一个模型，**monkeypatch** 两处做计时：
`feat_decoder.sample()`（每个 patch 的扩散采样）与 `audio_vae.decode()`
（最终的一次性解码），逐次调用、`mx.eval()` 强制物化（MLX 是惰性求值，
不强制物化的话计时会算到别的调用头上）。

机器：M1 Max / 64 GB，4bit，`inference_timesteps=10`（默认档），
参考音色 `男声`（`ref_text` 465 字）。

### 3.1 短句「现在几点了」（总 5.17s）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 参考音色上下文编码 + 初始 LM 前向（"首 patch"里包含的部分） | **2.86s** | 55% |
| 后续 patch 生成（稳态，每 patch 0.11–0.2s） | 2.24s | 43% |
| 最终 `audio_vae.decode()` | 0.07s | 1% |

### 3.2 中句「今天清迈多云转晴，最高32度，傍晚有阵雨，风不大。」（总 7.61s）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 参考音色上下文编码 + 初始 LM 前向 | **2.80s** | 37% |
| 后续 patch 生成（32 个 patch） | 4.56s | 60% |
| 最终 `audio_vae.decode()` | 0.20s | 3% |

### 3.3 关键对照实验：参考音色是不是真凶

同一句话「现在几点了」，分别用（a）当前配置的参考音色（465 字参考文本）
和（b）零样本（完全不给参考音频/文本）跑：

| 配置 | 首 patch 耗时 |
|---|---|
| 有参考音色（465 字参考文本） | **2.86 / 2.93s**（重复两次几乎不变） |
| 零样本（无参考） | **0.17 / 0.22s** |

**13–17 倍的差距，而且重复调用（同一进程内连打 5 次，含相同文本重复、
不同文本）这个 2.8s 都不会降**——排除了"MLX 图编译只发生一次、后面会命中缓存"
这个假设。真正原因是：**`generate()` 每次调用都会把 `ref_audio` 重新编码、
把 465 字的 `ref_text` 重新过一遍 `base_lm` 的初始前向**（"Initial forward pass"，
`enc_outputs, lm_cache = self.base_lm(combined_embed)`），这是一次性、每次都要
重付的固定成本，跟当次要说的话长短完全无关。

⚠️ **这与 `CLAUDE.md` 里原有的记录冲突，需要更正**："代价是每次合成重读一次
参考 wav（1–9 MB），相对 2.4–6s 的合成可忽略"——这条把成本理解成了**文件 I/O**
（读 wav 文件），实际成本是**计算**（把长达 465 字的参考文本过一遍语言模型），
量级是 2.8 秒，**不是"可忽略"，是短句合成里最大的单项开销**。

## 4. 两个可以独立做的优化，优先级不同

### 4.1 方案 A：缓存参考音色的编码结果（新发现，优先级更高）

**思路**：`base_lm` 在生成循环里已经在用 `lm_cache`（KV-cache 式对象）支持
"给定缓存、只算新增部分"的增量前向（`self.base_lm(inputs_embeds=curr_embed, cache=lm_cache)`）。
如果能把"参考音色部分"的前向结果**只算一次、缓存住**（比如在边车启动时，
或者第一次用到某个音色时），后续每次合成只需要在这个缓存好的前缀上追加
"这次要说的话"，理论上能把 2.8s 的固定成本降到接近于零。

**预期收益**（按 Phase 0 数字推算）：短句总耗时 5.17s → 约 **2.3s**（降 55%），
中句 7.61s → 约 **4.8s**（降 37%）。**不需要碰"分块流式"或改 HTTP 契约**，
纯粹是省掉一次重复计算。

**风险/不确定**：
- 需要验证 `base_lm`/`residual_lm` 的缓存对象能不能跨越"两次独立的 `generate()`
  调用"复用（现在是同一次调用内部循环复用，没验证过跨调用复用）。
- 音色库有多个音色（现在是"男声"/"女声"两个），缓存要按音色分别存，
  且用户切音色/切方言/切语气时 `instruct` 也会变——`instruct` 是拼进文本前缀里的
  （`text = f"({instruct}){text}"`），如果 `instruct` 影响了参考部分的编码，
  缓存的复用粒度需要重新设计（可能是"每个音色 × 每个 instruct 组合"缓存，
  而不是单纯按音色缓存）。**这一点 Phase 0 没验证，是 Phase 1 spike 要回答的问题**。
- 边车是常驻进程（已经是），缓存放内存里即可，不需要额外持久化。

### 4.2 方案 B：分块流式合成（原计划，优先级次之）

**思路**：见 §2——生成循环本来就是逐 patch 的，把"每攒够 N 个 patch 就解码一段、
流出去"接到对外接口，而不是等全部生成完才一次性 decode + yield。

**预期收益**：省掉的是"后续 patch 生成"那部分的**等待感**（4.1 §3.2 里的 4.56s），
不是消灭这部分计算——**总耗时基本不变**（这条链路的 RTF 实测在 1.4–4（短句更差，
因为固定成本占比更高）），跟 T3.4.8 句子级流水线是同一类"重叠等待"优化，
只是这次发生在 TTS 内部、粒度更细（160ms 一个 patch，而不是一整句）。

**风险/不确定**（原方案里已经列过，这里不重复）：
- 分段解码有没有拼接杂音，没测过。
- 是在 fork/包一层 `mlx_audio` 内部实现，不是公开 API，将来升级 `mlx_audio`
  版本可能对不上，需要锁版本号。
- `/speak` 端点契约不能改（ADR-0007 定死的），得新加一个流式端点，
  Rust 侧的 `CurlAudio`/`play_blocking` 也要跟着改成能边收边播，
  打断逻辑（`stop_playback()`）要同时通知边车停止继续生成。
- 粗估工作量 5–9 天（Phase 1 spike 1 天判生死，Phase 2/3 各 2–4 天）。

### 4.3 两者的关系

**不是二选一，是有先后**：方案 A 便宜（预计比 B 小一个数量级的工作量）、
风险低（不碰 HTTP 契约、不碰 Rust 播放侧）、且**对方案 B 也有用**——
如果方案 A 先落地，方案 B 的"分块流式"优化对象就变成了一个更短的
"后续 patch 生成"区间（省掉了前面 2.8s 固定成本的干扰），spike 阶段的
测量会更干净。**建议顺序：A 的 spike 先做，验证通了再排 B。**

## 5. 待验证的问题

### 5.1 方案 A：Phase 1 spike **已完成**（2026-09-19，`spike/t3413-tts-refcache/`）

**可行，但 `mlx_audio` 当前实现有一个阻塞性 bug，需要打一个标准补丁才能用。**

- **根因**：`MiniCPMModel.__call__` 构造因果 mask 时只考虑了"当前这批 L 个 token
  互相看"（`(L,L)` 方阵），没考虑"cache 里已经有 `offset` 个位置、新 token 还要
  看得见它们"——`Attention.__call__` 把 `k_cache`/`v_cache` 拼上新 k/v 后变成
  `offset+L` 长，但 mask 还是 `(L,L)`，直接 `ValueError: broadcast_shapes` 报错。
  这条路径在原实现里从没被走过：唯一用到 `cache` 的地方是自回归循环，
  每次只喂 1 个新 token（`L=1`），走的是另一个分支，这个 bug 才一直没暴露。
- **补丁标准**：mask 要覆盖 `(L, offset+L)`——前 `offset` 列全通过（已缓存内容
  永远可见），后 `L×L` 是常规下三角因果 mask。十几行代码，写在我们自己的
  `services/tts/` 里包一层，不改已安装的 `mlx_audio` 包本身。
- **打完补丁的实测**（同一份参考音色缓存，两句不同的新文本复用）：

  | | 建缓存（一次性） | 新文本前向 | 含后续 patch 生成 | 对照组（从头带参考） |
  |---|---|---|---|---|
  | 「现在几点了」 | 3.91s | **0.079s** | **1.242s** | 4.19s |
  | 「今天天气怎么样啊」 | （复用同一份） | **0.081s** | **1.379s** | 4.53s |

  **总耗时降到约 1/3**（4.19s→1.24s、4.53s→1.38s）——**比 Phase 0 按"耗时占比"
  估算的 55%/37% 更好**，因为新文本前向本身也从独立计算变成了近乎免费的续接。
  ⚠️ **建缓存本身要 3.91s，比对照组单次还贵**——只有同一音色被连续复用时才划算，
  边车要在启动时/首次用到某音色时建好并常驻复用。
- **正确性**：F0 中位数四条样本都落在参考音色的男声带内（85–155Hz），人耳
  `afplay` 抽样确认不是乱码；**不是逐字节比对**（扩散采样没固定 seed，方差是
  预期的）。**没测的**：`instruct`（语气/方言）切换是否影响参考部分编码结果
  （决定缓存要不要按"音色×instruct"分粒度）、长文本行为、缓存内存占用、
  边车重启后重建缓存的耗时。这些留给 Phase 2。

### 5.2 方案 B：**未开始**（按 §4.3 的建议顺序，方案 A 先落地再排）

分段 `audio_vae.decode()` 拼接出来的音频，跟一次性 decode 的结果逐样本比对，
接缝处有没有可听见的差异——这个问题 Phase 1 没碰，等方案 A 进 Phase 2 之后再排。

### 5.3 两者叠加后的真实首包延迟

还没有端到端数字——方案 A 目前测的是"总耗时"（含后续 patch 生成，仍是一次性
返回），不是"首包延迟"（那需要方案 B 的分块流式配合）。方案 A 单独落地后，
"说完话到听到全部回答"能从 4.2–4.5s 降到 1.2–1.4s；要把"听到第一个字"单独
压到亚秒级，还是要靠方案 B。

## 6. 明确不做的事

- ❌ 不改 `/speak` 现有契约——ADR-0007 定死了"接口一个字不用改"，方案 B 要流式
  就新开端点，不改老的。
- ❌ 不去动上游 `mlx_audio` 仓库本身——在 `services/tts/` 里包一层/继承，
  不直接改 `~/.agentear/llm/venv` 里装的包（升级会冲掉）。
- ❌ 本 ADR 不覆盖"要不要上真正的全双工架构"（Moshi 那类单模型语音进/语音出）——
  那是 ADR-0007 里 V2 的地界，本 ADR 只优化现有级联架构（ASR→LLM→TTS）里
  TTS 这一段的延迟，不推翻级联本身。
