## 1. 背景：愿景的一次重述

jason 2026-09-08 口述，把产品形态说清楚了一层。原话要点：

> 类似于一个实时双工的 AI。我们做的主要是语音部分。这个 App 有个按钮，
> 类似于打电话，打通了之后，双工可打断地实时跟我交流沟通。
> 我的语音你能识别并转化为内容，然后交给大模型 —— **当然这个大模型并不在
> 当前项目的工作职责范围内**，但我可以做一个 mock 的模型，简单回复一下。
> 比如我问今天天气怎么样，你去调用一下天气接口，告诉我「今天清迈天气还不错」。
> 用文字和语音**同时**输出，或者只用语音也可以。
> 语音是中文、英文和泰语，**可配置可选**，沟通前确认用什么语言，
> **过程中可以随时切换**，包括我说的和你输出的。
> 音色模型是可选的，并且要**真正像人类一样有感情**地说话。
> 所有模型必须本地化。

这段话与既有文档有五处实质冲突，逐条处理见 §2。

### 1.1 交付形态（本次新增的约束）

产品最终要能以三种方式被使用，**这决定了架构必须分层**：

1. **装到电脑上直接用** —— 现有 `.app` 形态，加一个「通话」入口
2. **配置自己的后台模型** —— 语音进、语音出，中间那个 LLM 由用户配置接上
3. **代码级集成到别的 agent / 模型** —— 要预留接口和说明文档

> **原有的录音输入法形态继续保留**，不被通话形态取代。

## 2. 与既有文档的冲突处理

| # | 愿景 | 既有文档 | 处理 |
|---|---|---|---|
| 1 | 实时全双工可打断 | `CLAUDE.md`：「2 GB 预算内做不到，v1 是打断式半双工」 | **分级**，见 §3 |
| 2 | 中英泰可配置、可随时切 | ASR 双链路（SenseVoice 无泰语 + whisper 泰语） | **统一到单引擎**，见 §5 |
| 3 | 有感情、音色可选 | ADR-0005 只验证了「能出声」 | 见 §6 |
| 4 | 打电话式实时对话 | M1 是快捷键 toggle 单次录音 | **新增会话层**，见 §4 |
| 5 | mock LLM（查天气） | 「LLM 不在职责内」 | LLM 仍不在职责内，但**要自带一个可跑通的默认实现**，见 §4.3 |
| 6 | 全本地 | 已是不可让步约束 | 一致，无冲突 |

### 2.1 关于「全双工」的措辞修订

`CLAUDE.md` 原文断言全双工「在 2 GB 预算内做不到」。**这个论断的前提已经不成立**
（M2 起预算 ≤9 GiB，目标机 64 GB），但结论方向仍然成立，原因变了：

**新的理由不是内存，是没有「已验证覆盖中泰且达到实时」的本地全双工候选**
——注意是「没有已验证的」，不是「不存在」。调研（2026-09-08）：

- NVIDIA VoiceChat 11B —— 真全双工、~450 ms 转轮延迟，但**仅英文**、
  许可证 OpenMDW 1.1 **仅研究用途**、aarch64 上 RTF 1.13 **达不到实时**
- PersonaPlex 7B（`speech respond`）—— 全双工，**语言覆盖与性能都还没测**

所以**不要再用「内存不够」解释为什么不做全双工**，那会误导后续决策。
**同时：PersonaPlex 那格没关掉之前，也不要写「不存在方案」。**

## 3. V1 / V2 分级：把内存门槛做成产品档位

jason 的原话：

> 不是所有人都有 64G 内存，所以可以有个降级的选择。内存不够的，
> 可以打断式的半双工。V2 就是实时全双工。

**这是产品决策，不是妥协**——它让 AgentEar 在低配机器上仍然可用。

| 档 | 形态 | 内存门槛 | 状态 |
|---|---|---|---|
| **V1** | 打断式半双工（VAD 检测到开口就掐掉 TTS） | **≤10 GB** | M3 目标 |
| **V2** | 实时全双工（边听边想） | 放宽到 **64 GB** 级 | **未排期**，见下 |

**V2 不占里程碑编号。** 它的**触发条件**是「出现经验证覆盖中文和泰语、
且在 Apple Silicon 上达到实时的本地全双工模型」——这个条件今天不成立，
排期也就无从谈起。条件满足时再立编号。
（初稿曾写「M4」，那个编号已经被「录音笔接入」占用，是笔误。）

**V1 不是 V2 的临时替代品，是长期保留的低配档位。** 两档共用同一套会话层
和引擎层，差别只在编排策略。

⚠️ **V1 的措辞纪律不变**（沿用 `CLAUDE.md`）：半双工解决「说完才轮到我」，
不解决「一边听一边想」，快速来回时能被感知到。**不要描述成「体感接近全双工」。**

## 4. 架构：R0–R3 四层，向下可换引擎，向上可换外壳

> ⚠️ **命名注意**：本仓库的 `L0–L3` 已经有确定含义
> （事实层 / 文档层 / 索引层 / 行动层，见 `CLAUDE.md` 存储语义一节）。
> **运行时架构一律用 `R0–R3`**，不要复用 L 前缀，否则同一个词两套含义。

```
┌────────────────────────────────────────────────────────────┐
│ R3 外壳层（三种，共享同一内核）                              │
│  A. AgentEar.app        桌面常驻：录音输入法 + 通话入口       │
│  B. agentear serve      HTTP / WebSocket，OpenAI 兼容        │
│  C. agentear mcp        MCP server，接入别的 agent 流程       │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│ R2 agentear-core（Rust lib）—— 可被代码级集成                │
│  会话生命周期 · 语言切换 · 持久化策略 · 既有 route/kb/index    │
│  ⚠️ 编排职责归属见 §4.4，不能和后端各编排一次                  │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│ R1 实时音频图（**同进程**，见 §4.3）                          │
│  音频 I/O · AEC · VAD · 轮次判定 · 打断控制                    │
└───────────────────────────┬────────────────────────────────┘
                            │ 进程边界只画在这里
┌───────────────────────────▼────────────────────────────────┐
│ R0 模型推理后端（子进程 / HTTP 边车，实现语言不受限）          │
│  AsrEngine │ sensevoice(现) │ whisper-th(现) │ qwen3-asr      │
│  TtsEngine │ say(现)        │ voxcpm2        │ indextts2      │
│  LlmEngine │ mock(自带)     │ mlx-dspark(现) │ 任意 OpenAI 端点 │
└────────────────────────────────────────────────────────────┘
```

### 4.1 这一层不是新发明的

`src/asr.rs:118` 的 `transcribe(wav, lang)` **已经在按语言分派**到
`transcribe_sensevoice` 和 `transcribe_thai` 两个子进程后端。R0 是把这个
既成事实提升为显式 trait，**不是推倒重来**。

### 4.2 设计原则（含一条被推翻的）

1. **LLM 永远是「可配置的外部端点」。** 我们不训练、不绑定、不内嵌 LLM。
   自带的 mock 只用来证明链路通，不是产品能力。
2. **能力矩阵，而不是「每个 trait 至少两个实现」。**
   ~~初稿写了「每个 trait 至少两个实现 + 每个都有零依赖默认实现」，这条是错的~~：
   `AecEngine` 目前只有 LocalVQE 一个候选，ASR / AEC 也不存在能满足产品语义的
   零依赖实现。硬套这条规则只会逼出没意义的 no-op 适配器。**改成：**

   | 引擎 | 多后端 | 零依赖默认实现 |
   |---|---|---|
   | AsrEngine / TtsEngine / LlmEngine | ✅ 必须支持切换 | TTS 有（`say`）、LLM 有（mock）、**ASR 没有** |
   | VadEngine / TurnCompletionEngine | 按会话模式声明 required/optional | — |
   | AecEngine | ❌ 当前仅一个候选，**先不抽象** | 无 |

   只有确实出现第二个候选、且有切换需求时才抽象接口。

3. **进程边界只画在 R0/R1 之间**（见 §4.3），不是「每个 trait 都跨进程」。

### 4.3 为什么 AEC / VAD 不跨进程

初稿把五个引擎一律放到进程外，**这在实时音频上行不通**：

- **AEC 必须同时拿到麦克风流和扬声器参考流**，两路要严格对齐时钟。
  跨进程传两路 PCM 还要保持采样级同步，代价直接体现在打断延迟上。
- 打断响应的验收阈值是 **< 300 ms**（`asr-selection.md` §4）。
  每加一次跨进程往返就吃掉一部分预算。

**所以：音频 I/O、AEC、VAD、轮次判定、打断控制共置在同一个实时音频图（R1）里；
只有模型推理后端（R0）跨进程。** 若将来确实要把 AEC 挪出去，
ADR 必须先给出帧协议、时钟对齐方案和延迟预算，并用实测证明达标。

#### 4.3.0 AEC 用 CoreAudio VPIO，不用 speech-swift（T3.4.0 实测定案）

`speech` CLI 与 `speech-server` **都没有 AEC 出口**（实测相关端点全部 404；
只有 `denoise`/`restore` 两个降噪命令，不是 AEC）。LocalVQE v1.4-AEC
**只存在于 Swift 库**（`import SpeechEnhancement`）。

→ 采用 **macOS Voice Processing I/O**
（`AVAudioEngine.inputNode.setVoiceProcessingEnabled(true)`）：
它是系统能力、不引入任何依赖，且天然与音频 I/O 共置，正合 §4.3 的要求。

**实测（benchmarks-m3.md §7.2，5 轮有效重测）**：VPIO 关时 **5/5** 完整复现 TTS 内容；
VPIO 开时 **5/5 都不再复现**（内容级 0/5 PASS），**但事件级仍 5/5——每轮残留一个单字**
（`嗯`/`金`/`啊`），**自触发率未到 0**。
⚠️ 早前写的「4/4」出自**第一批因扬声器静音而作废的数据**，已按有效重测更正。
补救靠最小语音时长 + 能量门限 + 播放期 gating，属 T3.4.2。
⚠️ VPIO 的抑制量**方差很大**（一轮里出现过开启后反而更高），不要用单次测量下结论。

### 4.3.1 VAD 与轮次判定是两件事，不是两个实现

~~初稿把 Silero 和 Smart Turn 并列成 `VadEngine` 的两个可选实现，这是错的。~~
它们是**串联关系**：

```
Silero VAD 检出静音  →  TurnCompletionEngine（Smart Turn）判断这个停顿
                          是不是「说完了」  →  最大静默时长兜底
```

Silero 回答「现在有没有人在说话」，Smart Turn 回答「这个停顿意味着轮次结束吗」——
后者正是用来**避免句中换气被误判成说完**。二选一会丢掉其中一个能力。

### 4.4 编排职责必须二选一，不能两边都做

`speech-server` 的 `/v1/realtime` **自带**轮次检测（`server_vad`）、
commit 和取消语义。如果 R2 也跑一套会话状态机，就会出现**两个状态机抢同一件事**。

**二选一，在 M3.0 定死：**

| 方案 | R2 的角色 | R0 的角色 |
|---|---|---|
| **A 自主编排** | 独占会话状态机与打断编排 | 只提供原子的 ASR / TTS 调用，**不用 `/v1/realtime`** |
| **B 委托编排** | 只管生命周期与持久化 | `RealtimeSessionBackend`，整段会话交给 `/v1/realtime` |

**倾向 A**：打断语义和持久化耦合紧，且 A 不把会话行为绑死在 v0.0.x 的上游协议上。
但这是 M3.0 要正式拍板的事，**不能默认它已经定了**。

### 4.5 持久化：实时通话是「有界丢失」，不是「零丢失」

~~初稿在会话内核里笼统写了「零丢失提交协议」，这与 `CLAUDE.md` 冲突。~~
既有措辞纪律（`CLAUDE.md` 存储语义一节 / `ingest-design.md` §3.7）是：

- **文件导入（路径 A）= 零丢失**，走完整提交协议后才 ACK
- **实时流（路径 B）= 有界丢失**，崩溃会丢掉最后一次 fsync 之后的部分

**通话形态属于路径 B。** 所以拆成两个策略，不要混写：

| 策略 | 用于 | 保证 |
|---|---|---|
| `BatchCommitPolicy` | 文件导入、M1 的快捷键录音 | 零丢失 |
| `StreamCheckpointPolicy` | 实时通话 | 定长时间片切分 + fsync 窗口内有界丢失 |

**下游路由仍然只消费 committed 的转写，不消费 provisional 的。**

### 4.6 mock LLM 的范围

一个「查天气 → 用语音说出来」的最小实现，用来：
- 证明 ASR → LLM → TTS 整条链路通
- 给集成方一个可照抄的 `LlmEngine` 实现样例

**它不是产品功能**，文档要写明这一点，避免被当成智能助手来评价。

### 4.7 输出模态

文字与语音**同时输出**为默认，可配置为「只语音」或「只文字」。
文字那一路直接复用现有的剪贴板 / 悬浮窗通路。

## 5. ASR：候选是统一到单引擎

> 实测数据见 [`docs/benchmarks-m3.md`](../benchmarks-m3.md)（2026-09-08）。

Qwen3-ASR 一个模型覆盖 30 语言（含中/英/泰）+ 22 中文方言，**自带语言识别**——
这直接实现「过程中随时切语言」而不需要用户手动切菜单。

泰语实测（22 条 Arm 语料，同一份 `reference.tsv`、同一套 CER 口径；
**但两侧的提示词表来源不同**，见 benchmarks-m3.md §2.1.0）：

| 配置 | 纯泰语 CER | 夹英文 CER | 英文词命中 |
|---|---|---|---|
| whisper A（v0.4.2 当前发布） | 3.9% | 31.1% | 8% |
| whisper D（词表 prompt） | 3.1% | 18.4% | 51% |
| Qwen3-ASR 1.7B + 24 词 canonical | **0.0%**（6/6 全对） | 23.1% | 44% |
| **Qwen3-ASR 1.7B + 47 词（与 D 同源词表）** | **0.0%** | 23.1% | 44% |

**换成与 whisper D 同源的完整 47 词拉丁词表，22 条结果逐字不变**，
所以词表口径这个变量已排除。

**本样本上纯泰语更好**（6 条、单一说话人，不足以断言总体）；
**夹英文两个指标都方向性偏向 whisper D**，但抽样不确定性未量化——
配对检验做不了，因为 whisper 的逐条 CER 没入库（benchmarks-m3.md §4.1）。
3 轮复跑 22/22 完全一致，解码是确定性的。
离线 RTF 0.074，**但实时指标（首包延迟、打断响应 <300ms、AEC 自触发率）一项都没测**。

⚠️ **这会推翻 ADR-0001 排除 Qwen3-ASR 的理由**（原因是「需要 Python + MLX 运行时」）。
speech-swift 是 **Swift 原生 + CLI/HTTP**，那条理由不再适用。
资源那一关已由 **2026-09-08 的分档拍板**解决（`CLAUDE.md`：
默认档 ≤2 GiB / 高资源档 ≤4 GiB，`speech_swift` 的 2.43 GiB 落在高资源档）。
**但「换默认引擎」是另一件事，仍需单独拍板**——那要看中英横比（T3.5.1）。

⚠️ **中文和英文链路还没横比。** 换默认引擎影响全部语种，
不能凭泰语结果推断 SenseVoice 该不该换。**拍板前这是个缺口。**

## 6. TTS：泰语和情感可能要分两个引擎

> 实测数据见 [`docs/benchmarks-m3.md`](../benchmarks-m3.md) §6。

筛选条件按优先级：**泰语 > 可商用 > 情感控制 > Apple Silicon**。

- **VoxCPM2**（Apache-2.0，48 kHz）：**是唯一能说泰语的候选**。
  `--voxcpm2-instruct` 用自然语言描述情感，实测客观有效
  （兴奋档 RMS 是中性档 6 倍、悲伤档时长更长）。
- **IndexTTS2**：情感控制强得多（`eager/happy/excited/angry/sad/afraid`
  预设 + 8 值向量 + 强度系数），**但只有 EN/ZH，没有泰语**。

→ 很可能的落点是**按语言选 TTS 引擎**：中英 IndexTTS2、泰语 VoxCPM2。
这正是 §4 引擎适配层要支撑的场景。

### 6.1 方言清单：一个新的硬约束（jason 2026-09-08 追加）

原方言清单（台湾话/广东话/香港话/英语/泰语）**追加了山东话、河南话**。
对照 VoxCPM2 官方支持的 9 种中文方言（四川话、粤语、吴语、东北话、河南话、
陕西话、山东话、天津话、闽南话）：

| 要求 | VoxCPM2 | 备注 |
|---|---|---|
| 普通话 / 粤语（广州话）/ 山东话 / 河南话 | ✅ | 触发方式待验证 |
| 香港腔 | ⚠️ | 用粤语近似 |
| **台湾腔** | ❌ | **闽南话 ≠ 台湾国语腔**，不要混为一谈 |

**台湾腔已降级（jason 2026-09-08 拍板）**：不再是选型的筛选条件。

这条影响很大——它把 **FireRedTTS3 从候选里拿掉了**。原本引入它的唯一理由
就是台湾腔（21 种中文方言），而代价是多一个运行时 + 声音克隆限学术使用。
台湾腔降级之后，**VoxCPM2 的 9 种方言足够覆盖当前需求**，不需要第二个 TTS 引擎。

香港腔仍用粤语近似。台湾腔记为**已知缺口**，将来真有需求再单独立项。

⚠️ **方言是否真的能靠 instruct 触发，目前没有客观判据**
（`language-id` 只到语言级，分辨不了中文内部方言），见 benchmarks-m3.md §6.2.2。

### 6.2 人耳验收状态

| 项 | 状态 |
