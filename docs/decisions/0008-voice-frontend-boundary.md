# ADR-0008：AgentEar 作为 Agent24 的语音前端（边界与接口）

- 状态：**已拍板（jason 2026-09-15）**
- 影响：冻结 AgentEar 的职责边界；**停止**在下游（执行 / 确认 UI / 初始化配置 /
  凭据 / 回执展示）继续开发；把这些留给宿主 Agent24。

## 0. 一句话

**AgentEar 负责「听见」和「说出」；谁去执行、怎么确认、写到哪、回执怎么展示，
是宿主（Agent24）的事。** AgentEar 只**提出**动作，**不执行**它。

## 1. 为什么这样切（jason 的原话与上下文）

jason 2026-09-15 的原话：

> 「AgentEar 这个定位呢，它就是语音交互……对于后边的命令执行界面的展示、
> 用户的确认、以及发送执行命令之后的界面的返回，包括执行命令本身，
> 实际上并不是 AgentEar 的本职工作。它至少概念上验证这些是可行了之后呢，
> 它要嵌入到 Agent24，我们的另外一个项目里，才能完成这些交互界面、命令执行等等。
> 所以当前这个结果我是接受的，但你要有相关的接口以及最基础的逻辑验证……
> 刚才我们讨论的配置啊、初始化这个就放在 Agent24 里，
> 所以这方面的尝试你预留接口，预留接口停止开发。」

据此：

| | 归属 | 为什么 |
|---|---|---|
| 音频采集（推键式）、ASR | **AgentEar** | 它的本职；且已经跑通、有实测 |
| TTS 合成与播放、打断 | **AgentEar** | 同上；播放的打断状态在 AgentEar 进程内 |
| 本机可逆动作（记笔记、切音色/语气/模式） | **AgentEar** | 不出这台机器，也不需要界面 |
| **指令的「提出」**（命中什么、要不要确认） | **AgentEar** | 需要本地 0ms 的查表能力 |
| **执行**（写 Notion / 发邮件 / 调 webhook） | **Agent24** | 需要凭据、需要界面、需要回执展示 |
| **确认 UI** | **Agent24** | AgentEar 没有界面（只有菜单栏） |
| **初始化配置**（token、database id、收件人） | **Agent24** | 是设置界面，不是语音 |
| **回执展示**（返回的 URL 等） | **Agent24** | 是界面 |

⚠️ **停止开发的含义**：`scripts/` 与 `src/` 里**不再新做**
「初始化向导 / 凭据管理 / 回执界面」。已经做出来的部分（v0.12.0 的语音二次确认、
v0.13.0 的回执读取）**保留**——它们在 AgentEar 单独运行时仍然有用，
而且正是「概念上验证可行」的产物。**但不要在这两条线上继续加功能。**

## 2. AgentEar 现在的完整能力（宿主可以直接用的）

```
┌─ AgentEar（一个 Rust 单二进制 + 两个本地边车）────────────────┐
│  推键式采集 ──→ ASR ──→ 文本 ──┬─→ 话术（对话模式）──→ TTS ──→ 播放
│                                └─→ 指令表查表 ──→ **提出一个动作**
└──────────────────────────────────────────────────────────────┘
        ↑ 事件/命令                                    ↓ 提出
   ┌──────────────────────── 宿主：Agent24 ────────────────────────┐
   │  确认 UI · 执行 · 凭据 · 初始化 · 回执展示 · 历史               │
   └──────────────────────────────────────────────────────────────┘
```

现有对外的入口（都已经能用，**不是计划**）：

| 入口 | 用途 |
|---|---|
| `agentear` | 守护进程：推键式录音 → 转写 → 上屏 →（对话模式）念出来 |
| `agentear --transcribe <wav>` | 只要转写（宿主自己拿到音频时用） |
| `agentear --ask <文本>` | 文本 → LLM → TTS → 播放（跳过 ASR） |
| `agentear --say <文本>` | 只做 TTS + 播放 |
| `agentear --match-command <文本> [--json]` | **只提出动作，绝不执行** ← 边界主入口 |
| `agentear --run-command <文本> [--reply]` | AgentEar 自己执行一轮（**仅供自测，宿主别用**） |
| `agentear --commands` / `--add-command` | 指令表读写 |
| `agentear --diagnose` | 环境自检（权限、设备、依赖） |

## 3. 接口契约：`agentear.proposal/1`（**已冻结**）

`agentear --match-command "<一句话>" --json` 输出**一个 JSON 对象**到 stdout：

```json
{
  "schema": "agentear.proposal/1",
  "text": "发邮件给 a@b.com 讨论 AEC",
  "normalized": "发邮件给abcom讨论aec",
  "matched": "发邮件给",
  "rest": "a@b.com 讨论 AEC",
  "action": { "type": "open_url", "url": "mailto:{rest}" },
  "needs_confirm": true,
  "prompt": "要打开邮件草稿：a@b.com 讨论 AEC。确认就按一下键，或者说「确认」。",
  "command_count": 9,
  "commands_path": "/Users/…/commands.json"
}
```

字段语义（宿主实现时按这张表来）：

| 字段 | 含义 | 宿主该怎么用 |
|---|---|---|
| `schema` | 契约版本 | 按版本分支；变了就说明不兼容 |
| `matched` | 命中的短语 | `null` = **没命中**，此时走对话那条路 |
| `rest` | 槽位（**原文**，保留大小写与点号） | 显示给用户看 |
| `action.type` | `builtin` / `open_url` / `http_post` | 三种，**封闭集合** |
| `action.url` / `body` | URL 或 JSON 模板，含 `{rest}` `{text}` | 宿主自己填。⚠️ 填进 **URL** 时要百分号转义（AgentEar 侧的 `fill` 就是这么做的）；填进 JSON body **不要**转义 |
| `needs_confirm` | 会不会把内容送出这台机器 | **为真就必须先确认** |
| `prompt` | 念给/显示给用户的问句 | ⚠️ **只有 `needs_confirm` 为真时才存在**（否则是 `null`） |
| `command_count` / `commands_path` | 指令表规模与位置 | 排错用；宿主可以提供「打开指令表」 |

**两条硬约束**（宿主必须照做，否则这个接口没意义）：

1. **`prompt` 与将要执行的内容同源**：它由 AgentEar 从 `text` + `hit` 生成，
   宿主显示它、执行时也用同一份 `rest`/`text`。**念 A 发 B 会让确认变成走过场。**
2. **`--match-command --json` 永不执行任何东西。** 这条有测试与人工验证钉着。

## 4. 最基础的逻辑验证（已做）

`scripts/agent24-standin.py` —— **假宿主**，演示并验证这条路走得通：
问 AgentEar 拿 proposal → 自己显示 → 自己确认 → **自己执行** → 自己展示回执。

```bash
scripts/agent24-standin.py "发邮件给 a@b.com 讨论 AEC"   # 交互式确认
scripts/agent24-standin.py "搜索 rust async" --yes       # 跳过确认
scripts/agent24-standin.py "今天天气怎么样"              # 不命中 → 提示走对话
```

它**故意不调用 `--run-command`**——用了就等于把执行又塞回 AgentEar，
而那正是这条 ADR 要分开的东西。

已验证：① 用户拒绝 → 什么都没执行；② 本机动作 → 不需要确认；
③ 没命中 → 提示转对话；④ `http_post` 的执行与回执（含 HTTP 401 的失败如实报）
由**宿主侧**完成。

## 5. 对 Agent24 的诉求（需要你们回答，否则只能靠猜）

1. **事件怎么给你？** 三种都可以做，但要**选一个**：
   (a) 子进程 + stdout 的 JSON Lines（最简单，无端口）；
   (b) 本地 HTTP（`127.0.0.1`，和现有两个边车同样的「连接优先、拉起兜底」形态）；
   (c) WebSocket 事件流。
   **我需要一个确定的契约**。我倾向 (a) 起步、(b) 作为长期形态。
2. **热键归谁？** 这是最实际的冲突点：**两个 app 都装 CGEventTap 会都收到右 Command**，
   而「谁负责录音」必须只有一个。请定：Agent24 持有热键并通知 AgentEar，
   还是 AgentEar 持有热键并把事件推给 Agent24？（后者改动小，但需要一条进程间通道。）
3. **麦克风与播放的归属。** AgentEar 现在是「采集 + 播放」在同一个进程里，
   打断（按录音键先掐掉正在播的回答）靠进程内状态。
   如果 Agent24 把播放拿走，**打断语义要重新定义**（谁记住「正在播什么」）。
4. **谁配置模型与音色？** LLM/TTS 两个边车、音色库、`commands.json`
   现在都在 AgentEar 这一侧（`~/.agentear/`）。宿主是要**接管**这些配置，
   还是只读？如果接管，`~/.agentear/config.json` 就不再是唯一真相。
5. **TCC 权限是 per-app 的。** 麦克风与辅助功能要**各自授权**。
   如果音频采集留在 AgentEar，Agent24 不需要麦克风权限；
   一旦搬过去，**用户要重新授权一次**。
6. **确认之后要不要「回执留档」？** AgentEar 现在把回执打在日志/标准输出里，
   **没有落库**。如果宿主负责展示，历史记录也该由宿主存——请确认。

## 6. 明确不做的事（避免重复讨论）

- ❌ AgentEar 里做**初始化向导 / 凭据管理**（v0.13.x 讨论到这里就停了）
- ❌ AgentEar 里做**回执界面 / 历史列表**
- ❌ AgentEar 里做**多轮追问**（「发给谁？」）——2B 模型记不住上下文，
  硬做只会得到更会编的幻觉；要做得先换模型（`talk_llm_url` 指过去即可，Rust 侧不用改）
- ❌ AgentEar 里做**执行**（除了本机可逆动作）
