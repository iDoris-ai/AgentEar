# 通话链路实测：VoxCPM2-4bit + MiniCPM5-2B（2026-09-14）

机器：MacBook Pro M1 Max / 64 GB · macOS 26.4.1 · macOS 内建麦克风与扬声器
运行时：`~/.agentear/llm/venv`（Python 3.11.15，mlx 0.32.2，mlx-lm 0.31.3，mlx-audio 0.5.1）

> **这一份与 `benchmarks-m3.md` 的关系**：那份测的是 **speech-swift（bf16 路径，
> Swift CLI）**；这一份测的是 **MLX 4bit 路径（Python 边车）**。
> **两者不是同一条路径，数字不能互相引用、也不能混着横向比较。**
> 例如 `benchmarks-m3.md` §3.1 的「VoxCPM2 单次峰值 1.54 GiB」是 bf16 的
> speech-swift 进程；本文件里 4bit 的 2.5 GB 是 Python + MLX 进程的峰值。
> **「4bit 更省内存」这句话本文不支持**——两者口径不同。

复现：

```bash
scripts/setup-talk.sh                                   # 按需下载两个模型（不随包分发）
scripts/serve-talk-llm.sh                               # LLM 边车 :8794
scripts/serve-tts.sh                                    # TTS 边车 :8765
scripts/talk-e2e.sh --text '今天天气怎么样？' --lang zh   # 端到端
```

---

## 1. 结论先说

1. **整条链路通了，中英泰三种语言都真的跑通了一遍**（§4）：
   说一句 → ASR → MiniCPM5-2B → VoxCPM2-4bit → 播放出声。
2. **一轮的时延是「秒级」，不是「毫秒级」**（§3）：ASR 0.2–0.5s（中英）+
   LLM 0.66–0.85s + **TTS 合成 2.6–5.1s** + 播放（按音频长度）。
   **TTS 是这条链路里最慢的一环**，而且它不可流式（§3.3）。
3. **VoxCPM2-4bit 在本机实测能出声、能说泰语、48 kHz**（§2）。
   ⚠️ **但 4bit 与 bf16 的质量对比没做**，所以「4bit 够不够好」本文答不了。
4. **MiniCPM5-2B 的中英可用，泰语在能力边界外**（§5）。
   模型卡只声明 `en, zh`；实测能听懂泰语、能产出泰语，但**提示词不钉死语言时
   会用中文回答**。不要把泰语质量写成与中英同级。
5. **天气那句话是本地写死的场景，不是天气接口**（ADR-0007 §4.6）。
   它在链路里的作用是「让模型有东西可说」。
6. **AEC 一格没动**：本轮是**推键式**打断（按键即掐），
   VAD 自动打断、双讲、误打断率、端到端打断延迟 <300 ms **全部仍未测**（§6）。

## 2. TTS：VoxCPM2-4bit

模型 `mlx-community/VoxCPM2-4bit`（Apache-2.0，base `openbmb/VoxCPM2`，
模型目录 **HF 报 2.3 GB**（`du -sh` 显示 2.1G，APFS 块计数口径不同）/ 2.38B 参数），经 `mlx-audio` 在本进程内常驻。

| 指标 | 实测 |
|---|---|
| 采样率 / 格式 | **48000 Hz，单声道，16-bit PCM** |
| 模型加载 | **0.86 s**（`/health` 的 `load_seconds`） |
| 进程峰值 RSS | **约 2.5 GB**（`/usr/bin/time -l`，含 Metal 缓冲） |
| 一句（3–5 秒音频）HTTP 端到端 | **2.6 – 3.9 s**（热，见 §3） |
| 三语是否出声 | zh ✅ / en ✅ / th ✅ |

⚠️ **同一个模型的多次生成时长不固定**：同一句泰语两次跑出 3.68s 与 4.80s 的
音频。VoxCPM2 是扩散式生成且**没有固定 seed**，这与 `benchmarks-m3.md` §6.2
记的「同参数重跑本来就会产生不同输出」是同一件事。**别把输出时长当成可复现的指标。**

### 2.1 HTTP 契约没变，换的是后端

`services/tts` 的契约（`POST /speak {text,lang} → audio/wav`、`GET /health`、
`GET /voices`）**一个字没改**，只是 `--backend` 默认从 `say` 变成了 `voxcpm2`。
`--backend say` 仍然是可用的零依赖保底（ADR-0007 §4.2 表格里 TTS 那一格）。

`/health` 现在会报 `backend` / `model` / `sample_rate` / `load_seconds`——
**这是为了让「对面到底是哪个后端」可查**：换了模型却连着旧服务，
是这类边车里最容易发生、也最难发现的错（`serve-llm.sh` 记过同源的坑）。

### 2.2 一个必须记下来的坑：MLX 的 stream 是线程局部的

**症状**：服务起来、`/health` 正常，第一个 `/speak` 请求把**整个进程干掉**：

```
libc++abi: terminating due to uncaught exception of type std::runtime_error:
There is no Stream(cpu, 1) in current thread.
```

**根因**：`ThreadingHTTPServer` 的请求跑在工作线程里，而 MLX 的 stream
属于**创建它的那条线程**。权重在主线程加载、在工作线程推理时，
崩点出现在**惰性 `mx.array` 第一次被求值**的地方（`np.asarray`）。

**为什么这值得单独写一节**：我第一版探针在主线程加载、在工作线程里读了
`seg.audio.shape[0]`，**报「通过」**。`.shape`/`.size` 是元数据，**不触发求值**——
探针根本没走到会崩的那一步。这和 `benchmarks-m3.md` §7.5 记的两条教训是同一类：
**测量设计的缺陷比测量误差危险得多**。

**修法**：load、generate、分段拼接、numpy 转换、打包 WAV **全部放在同一条专用
线程**上，HTTP 工作线程通过队列投递任务（`services/tts/backends.py` 的
`VoxCpm2Backend._mlx_thread`）。副作用正好是我们要的：合成天然串行。

### 2.3 没有流式可给（TTS 这一侧）

`mlx_audio` 的 `generate` 是**生成器**（不是返回单个结果），长文本会分成多段
要按顺序拼起来。但实测**短句只产出一段**，也就是「等生成完才拿到音频」——
`first_chunk` 与 `total` 基本相等。

→ **TTS 侧的首包延迟 ≈ 总合成时间**，一次调用有个**约 2.4 s 的固定开销**
（实测：23 字的回答合成 6.50 s、30 字的 2.92 s——**方差比长度影响还大**）。
「先出几个字就开念」在 TTS 这一侧目前做不到，**不要写成「TTS 已支持流式」**。

## 2.5 句子级流水线：边出边合成（v0.10.0，2026-09-14）

**LLM 侧可以流式**（`stream: true`，SSE），TTS 侧不行（§2.3）。所以做的不是
「音频流式」，而是**把「等 LLM 说完」和「等 TTS 合成」这两段重叠起来**：
LLM 一出第一个句子就送去合成，合成一段播一段，后面的句子在播放期间继续合成。

### 实测（M1 Max / 64 GB，同一句提问各 3 次）

| | 首字起播 | 整轮墙钟 |
|---|---|---|
| **整句路径**（`--ask --no-stream`） | **3.27 / 4.00 / 6.94 s**（= LLM + TTS） | — |
| **流式路径**（`--ask`，默认） | **2.27 / 2.29 / 2.60 / 2.61 / 2.78 s** | 10.40 s（首字 2.27 + 播 7.85 = 10.12，**句间无空隙**） |

- **收益是真的，但没有到「1 秒」**：首字从 3.3–6.9 s 降到 **约 2.3–2.6 s**，
  而且**不再随回答长度增长**（整句路径会）。回答越长，省得越多。
- **地板是「一次 TTS 合成」**：首字 ≈ 首句生成（约 0.2 s）+ 单句合成（约 2.4 s）。
  想再往下压，要压的是 TTS 那 **2.4 s 固定开销**，不是 LLM——而 LLM 在这里
  只占 0.35–0.44 s。**不要把这条优化说成「压到了 1 秒」。**
- LLM 侧逐字返回（一个 chunk 一个字），所以切句必须容忍「句末标点正好是
  一个碎片的最后一个字符」：**要等下一个碎片才敢切**（详见 `SentenceSplitter`）。
- 句间**没有可测的空隙**：生产者合成下一句（约 2.4 s）快于播放上一句（约 2.5 s 起），
  墙钟 ≈ 首字 + 播出时长。

### 这一版踩到的两个「静默」坑（都实测到过）

1. **流式 URL 少了路径** —— `post_json` 的 `url` 是 base（`…:8794`），路径由
   传输层自己拼。流式那条忘了拼 `/v1/chat/completions` → **404**，
   被上层当成「流式不可用」，**静默退回整句路径**。
2. **退回路径不喂下游** —— 运行期退回整句路径时如果不再调一次 `on_delta`，
   下游（切句 → 合成 → 播放）根本不会启动：**有文字、没声音**，
   而日志里一切正常。

这两条的教训是同一条：**「退回老路」的分支必须有输出**，
否则它比慢得多更糟——用户看到文字出来了，却不知道为什么没声音。

## 3. 一轮的时延构成

| 环节 | 实测 | 说明 |
|---|---|---|
| ASR（中/英，SenseVoice） | **0.18 – 0.49 s** | 复用 M1 链路，`--transcribe` 实测 |
| ASR（泰语，whisper） | **⚠️ 本环境数字无效**，见 §3.1 | |
| LLM（MiniCPM5-2B-4bit） | **0.35 – 0.85 s** | 一句问答，关掉 thinking 后 |
| TTS 合成（VoxCPM2-4bit） | **2.4 – 6.5 s** | 有一次**约 2.4 s 的固定开销**，再随长度走 |
| 播放 | 按音频长度 | 48 kHz 音频，`afplay` 子进程 |

**合计（中英）约 4–7 秒一轮。** 这是「打电话」体感的真实水平——
**它不是毫秒级的东西，也不该被描述成毫秒级。**

⚠️ **v0.10.0 的句子级流水线（§2.5）把「首字起播」压到约 2.3–2.6 s**，
但**一轮的总时长基本没变**（省的是等待，不是计算）。引用时要说清是哪一个指标。

### 3.1 ⚠️ 泰语 ASR 的时延在这个环境里测不了

- 本 sandbox 实测：`whisper-cli` 单次调用 **约 19.9 s**（两次都是）
- 但 `docs/data/thai-coldstart-raw.txt`（2026-08-28，正常 Terminal）记的是
  **wall 0.96 s**、`load_ms` 190 ms
- 关掉 GPU（`-ng`，纯 CPU）**5.9 s** —— GPU 比 CPU 还慢 3 倍

→ 指向 **Metal 着色器缓存写不进去**（sandbox 禁止写仓库外的
`~/Library/Caches`），每次调用都要重新编译着色器。

**结论：任何在本 sandbox 里测出的 whisper / Metal 时延都不可引用。**
要报这个数，必须在正常 Terminal 里复测。本文因此**不给泰语 ASR 的时延结论**。

### 3.2 长跑与泄漏没测

上面全是短句、单次调用的读数。**常驻反复推理的稳态 RSS、有没有泄漏都没测。**
ADR-0001 那次横比里 SenseVoice 的 RSS 是随音频长度线性涨的（0.52 MB/s），
**同样的长跑测试在这条路径上还欠着。**

## 4. 端到端验收（`scripts/talk-e2e.sh`）

脚本做的事：`say` 合成问句（只为造输入音频）→ `agentear --transcribe` → LLM
→ TTS → 写出回答 WAV。**全程离线。**

| 语言 | 听到的（ASR） | 回答（LLM） | 回答音频 |
|---|---|---|---|
| zh | `今天天气怎么样？`（逐字正确） | `今天清迈多云转晴，最高 32 度，傍晚有阵雨，风不大。` | 48 kHz / 5.12 s |
| en | `What's the weather like today.`（逐字正确） | `Today's weather in Chiang Mai is partly cloudy with a high of 32 degrees, and there's a chance of a light shower in the evening.` | 48 kHz / 6.88 s |
| th | `วันนี้อากาศเป็นอย่างไรบ้าง`（逐字正确） | `วันนี้อากาศเป็นแบบมีฝนตกบ้าง แต overall อากาศค่อนข้างสบาย` | 48 kHz / 3.68 s |

### 4.1 「说的确实是目标语言」——回环转写

拿生成的音频再喂回**本仓库自己的 ASR**（这条是客观证据，不是听感）：

| 合成输入 | 回环转写结果 | 判定 |
|---|---|---|
| `今天清迈天气还不错，最高三十二度。` | `今天青迈天气还不错，最高32度。` | ✅ 同义（清迈→青迈是同音误识，数字被规范化） |
| `It is nice in Chiang Mai today, around thirty-two degrees.` | `It is nice in Chiang Mai today around 32 degrees.` | ✅ 逐字 |
| `วันนี้ที่เชียงใหม่ อากาศดี อุณหภูมิสามสิบสององศา` | `วันอีกที่เชียงใหม่อากาศดีอุณหภูมิ 32 องศา` | ✅ 基本逐字（`วันนี้ที่`→`วันอีกที่`） |

**它证明的是语种与内容正确**（没读成别的语言、也不是乱码），
**不能**证明发音地道、也不能替代人耳验收。⚠️ **JASON 还没听过这一批**，
样本在 `vendor/models/talk/out/e2e/`（不入库）。

### 4.2 ⚠️ 泰语输出不稳定，有两种实测到的坏形态

把提示词的语言约束从「用泰语回答」改成「**必须只使用泰语回答，
一个其他语言的词都不要出现**」之后，同一句泰语问题得到过纯泰语回答
（`วันนี้อากาศเป็นแบบมีฝนตกบ้างในตอนเย็น อุณหภูมิประมาณ 32 องศา`）。
但**多跑几次就能看到它不稳定**，两种坏形态都实测到过：

| 坏形态 | 实例（都是 MiniCPM5-2B 产出，不是 ASR 的问题） |
|---|---|
| **混进英文词** | `วันนี้อากาศเป็นแบบมีฝนตกบ้าง แต overall อากาศค่อนข้างสบาย` —— 夹了 `overall` |
| **把问句原样退回来** | 问 `วันนี้อากาศเป็นอย่างไรบ้าง`，答也是 `วันนี้อากาศเป็นอย่างไรบ้าง`（**一次**，端到端脚本那一轮） |

复测口径：`agentear --ask 'วันนี้อากาศเป็นอย่างไรบ้าง' --lang th` 连跑 3 次，
**3 次都给了泰语回答**，其中 **2 次夹了 `overall`**、1 次干净。
复述那一次是更早的端到端脚本里出现的（同一天、同一个模型、同一套提示词）。
→ **两种坏形态都不是每次都能复现**，所以「能说泰语」这句成立，
但**「稳定说纯泰语」这句不成立**，别写成后者。

**复述已经被程序挡住**：`src/talk.rs::is_echo` 在去标点去空白后比较回答与问句，
完全相同（且长度 ≥4 字符）就判定为复述，**这一轮不播**并记日志。
理由很直接——不是回答的东西念出来，用户听到的是自己的问题，
而他会觉得「这东西坏了，还说不清哪坏了」；**宁可这一轮没有声音**。
⚠️ 这是**宽松判据**（只判「一模一样」），不判语义：误杀一个好回答的代价
比放过一次复述更大。

→ 结论：**提示词对 2B 模型很敏感，而泰语整体在它的能力边界外**
（模型卡只声明 `en, zh`）。要把泰语做稳，应当**换模型**——
`talk_llm_url` 指向任何 OpenAI 兼容端点即可，**Rust 侧一个字不用改**。

### 4.3 推键式的完整一轮（`--talk-turn`，不走麦克风）

`scripts/talk-e2e.sh` 验的是「脚本把三段拼起来」，**推键式链路本身**在守护进程里，
入口是录音键——按键、麦克风权限、TCC 都没法无人值守复现。为此加了
`agentear --talk-turn <wav>`：它跑的是守护进程**同一个** `answer_out_loud`，
只是文字从 wav 来而不是从麦克风来。

三语各跑一次（问句由 `say` 合成、16 kHz 单声道）：

| 语言 | ① 听到（ASR） | ② 回答（MiniCPM5-2B-4bit） | ③④ 播放 |
|---|---|---|---|
| zh | `今天天气怎么样？`（0.14s） | `今天清迈多云转晴，最高32度，傍晚有阵雨。` | 播完 4.82s |
| en | `What's the weather like today.`（0.11s） | `Today in Chiang Mai is partly cloudy with a high of 32 degrees.` | 播完 5.05s |
| th | `วันนี้อากาศเป็นอย่างไรบ้าง`（19.33s，见 §3.1 环境无效） | `วันนี้อากาศเป็นแบบมีฝนตกบ้างในช่วงบ่ายอุณหภูมิประมาณ 32 องศา` | 播完 4.05s |

会话状态机每一轮都记到了（日志 `通话统计：1 轮，语言 zh/en/th`），
**语言按 `--lang` 走而不是被配置改掉**。

#### ⚠️ 这个入口当场抓出一个真 bug（值得记下来）

第一版 `--talk-turn` 漏了「等价于按下键」的 `begin_turn()`：会话还停在 `Idle`，
于是 `finish_listening` / `turn_ready` **全部被状态机按非法转移拒掉**，
而拒绝只写 `warning`——最终统计打印的是**自相矛盾的「0 轮」**，
链路却看起来一切正常（转写有、回答有、声音也出来了）。

两个教训：
1. **状态机的拒绝必须是可观察的**：只写 warning 的话，一个「什么都没记上」的
   静默失败会伪装成成功。现在 `--talk-turn` 会把它喊出来。
2. **端到端入口的价值正在于此**：它跑的是产品代码，不是为测试另写的一条路。

#### 打断机制本身有用例（`cargo test -- --ignored stop_playback`）

造一段 5 秒的 440 Hz 正弦波，起播 → 等 600 ms → `stop_playback()`，
断言实际播放时长 **< 4s**（实测远小于），并且再次调用返回 `false`（幂等）。
⚠️ 这条用了 `#[ignore]`：`afplay` 在 macOS 上恒在，但**没有可用输出设备**时
（CI runner / 无声卡容器）它会直接失败，而那不是「打断坏了」。

### 4.4 `--diagnose` 会分别报两个边车

```
实时通话（可选，需要两个边车）:
  开关: ✅ 开
  LLM 引擎: openai_compat @ http://127.0.0.1:8794
  TTS 引擎: http @ http://127.0.0.1:8765
  ✅ LLM 边车在跑
  ✅ TTS 边车在跑
  通话语言: zh
```

⚠️ 那句「开关是开的，但 X 边车没起」**只在真的缺东西时**才打。
第一版写成无条件的，结果两个边车都在跑也照样喊——**自检骗人比没有自检更糟**
（这个仓库为这条栽过不止一次），已修。

## 5. LLM：MiniCPM5-2B-4bit（`mlx-community/MiniCPM5-2B-mlx-4Bit`）

| 指标 | 实测 |
|---|---|
| 模型目录 | HF 报 1.4 GB（`du -sh` 1.3G）；4bit affine，group_size 64 |
| 峰值内存 | **1.59 GB**（`mlx_lm.generate` 报的 peak memory） |
| 单句生成 | 36 tokens / 137 tok·s⁻¹，**0.66 – 0.85 s**（走 HTTP） |
| 默认吐思考段？ | **是**，见 §5.1 |

### 5.1 必须关掉 thinking

MiniCPM5 的 chat template 会在 assistant 开头插 `<think>`，
**默认先推理再回答**。实测问「今天天气怎么样」，原始输出是：

```
首先，我需要确认用户的问题是关于天气的。
接下来，我需要确保回复简洁。
...
</think>
今天天气很好。
```

通话形态下这一段有三个害处：会被念出来；多几百毫秒到几秒首字延迟
（而 V1 的打断阈值是 300 ms）；占掉 `max_tokens` 预算。

**两道防线都做了**：
1. 边车侧 `--chat-template-args '{"enable_thinking": false}'`（模板支持，
   写法照 M2 对 Ornith 用 `--no-thinking` 的同一道理）
2. 客户端侧 `talk::strip_thinking` 再剥一次——**换模型之后不保证还有那个开关**，
   而这道防线不依赖任何具体模型的行为

### 5.2 语言覆盖

模型卡 `language: en, zh`。实测：
- 中文问 → 中文答 ✅，英文问 → 英文答 ✅
- 泰语问 → **能听懂**（能正确复述问句含义），**能用泰语答**，但提示词不钉死时
  会切回中文；钉死之后这次得到纯泰语

**结论：中英可用；泰语是「能跑通、质量未验收」。**
需要稳定泰语时应当换模型——`talk_llm_url` 指向任何 OpenAI 兼容端点即可，
**换模型不改一行 Rust**（ADR-0007 §4.2 原则 1）。

### 6.1 措辞纪律

- 本轮实现的是**打断式半双工**：解决「说完才轮到我」，**不解决「一边听一边想」**。
  **不要写成「体感接近全双工」。**
- 「通话链路跑通」≠「V1 验收通过」。V1 的出口判据是 §6 表里那三条，**一条都没测**。

## 7. 复现与产物

```bash
# 模型（按需下载，不随包分发）
scripts/setup-talk.sh

# 两个边车（分别起，各自可单独重启/崩溃）
scripts/serve-talk-llm.sh          # :8794，换模型改 AGENTEAR_TALK_LLM_MODEL
scripts/serve-tts.sh               # :8765，退回 say 用 AGENTEAR_TTS_BACKEND=say

# 端到端（离线）
scripts/talk-e2e.sh --text '今天天气怎么样？' --lang zh
scripts/talk-e2e.sh --text "What's the weather like today?" --lang en
scripts/talk-e2e.sh --text 'วันนี้อากาศเป็นอย่างไรบ้าง' --lang th

# 只测后半段（不碰麦克风）
./target/release/agentear --ask '今天天气怎么样'
./target/release/agentear --say 'สวัสดีครับ' --lang th
```

产物在 `vendor/models/talk/out/e2e/`（**不入库**，`vendor/models/` 已 ignore）。
在本仓库里模型权重放在 `vendor/models/talk/`，正式安装路径是
`~/.agentear/talk/models/`（`scripts/setup-talk.sh` 的默认值，
本机 sandbox 不允许写仓库外，所以本轮实测用的是仓库内路径）。
